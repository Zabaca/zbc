# d1 — new

**Consumers:** ceo, leeandco, foothill-metabolic, web, crux (5)
**Deployed in production by:** crux, foothill-metabolic, web
**Independent lineages:** at least 2 — three of the five are ~111-119 lines with
identical key sets (copy-paste siblings); crux and leeandco each went further.

## What they needed

A Cloudflare D1 database with a lifecycle owned by infra rather than as a side
effect of `wrangler deploy`. Five consumers wrote it. zbc has `turso` and `r2`
and no D1 — `git log --all -- .../modules/d1` is empty, so this has never
existed upstream on any branch.

crux rejected Turso explicitly and recorded the resulting hole in an ADR
(`docs/adr/0004-cloudflare-stack.md:7,17`): *"D1 has no zbc module. The database
is created once with `wrangler d1 create` and bound by id."*

## The interface, from 5 implementations

**Unanimous** — config `{accountId, databaseName}`, outputs
`{databaseName, databaseId}`. Idempotent list-then-create, and a `destroy` that
tolerates an already-absent database.

**Divergent** — the schema question, and only here:

| Consumer | Extra config | Doing what |
|---|---|---|
| crux | `statements`, `additiveColumns` | converges schema in the same apply |
| leeandco | `apiToken` | takes its token from an imported instance, not a fixed secret |

crux's split is the interesting design: `statements` are end-state
(`CREATE TABLE IF NOT EXISTS`, replayable); `additiveColumns` are
`ALTER TABLE … ADD COLUMN`, where SQLite has no `IF NOT EXISTS`, so a
"duplicate column name" error is swallowed as the success case
(`isDuplicateColumn()` at `index.ts:81-84`, used `:141-149`). The same arrays
feed the Worker's own `applyD1Schema()` and its workerd tests.

## The module does not close the gap it was written for

**Every implementation still hardcodes `database_id`.** crux:
`apps/cloud/wrangler.jsonc:58`, with a comment saying so. foothill:
`packages/foothill-inbox/wrangler.jsonc`, literal
`1ddaec5c-030a-4edf-919e-2a54ecb6568a`. `cloudflare` has an `r2Bindings`
resolver and no D1 equivalent, so a provisioned `databaseId` cannot reach the
Worker that reads it.

**And nothing runs the migrations.** foothill declares `migrations_dir` in
`wrangler.jsonc` and ships `0001_better_auth.sql` / `0002_operators.sql` — and
a repo-wide grep for `wrangler d1 migrations apply` returns **zero hits**. No
script, no workflow step, no runbook. Both migrations were applied by hand.
Their `turso` module has `migrationsDir`; their `d1` has no equivalent, and
`cloudflare` has no post-deploy hook to put one in.

Two of the five modules carry an unedited doc comment from `r2` — foothill's
says *"Exists so bucket lifecycle is owned by infra"* inside a D1 module
(`d1/index.ts:8-11`), ceo's likewise. They were cloned from `r2`'s shape, which
is a fair signal that the module part was the easy part.

## What it takes upstream

The module itself is settled — build the unanimous interface. But shipping only
that leaves both real gaps open, and five consumers have already demonstrated
they will hardcode the id and hand-run the migrations. This case is really
three:

1. the `d1` module (easy, agreed interface)
2. output → `wrangler.jsonc` binding resolution — see
   [engine-output-wiring](./engine-output-wiring.md)
3. a post-deploy hook so migrations have a home — see [cli-gaps](./cli-gaps.md)
