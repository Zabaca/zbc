# d1 — upgrade

**Consumers:** cedarpad, ceo, crux, foothill-metabolic, leeandco, qom, railmid, varnick, web (9)  ·  **Deployed in production by:** cedarpad, ceo, crux, foothill-metabolic, leeandco, qom, railmid, web

## What they needed

A D1 database infra owns, its id reaching the Worker without pasting, and on every deploy a schema no older than the code reading it. The incidents are in the schema: cedarpad's API returned 500s when edge code shipped ahead of an `ALTER`, crux served a sign-in page with no auth tables, and web, qom and leeandco document 500s until a hand-run migration lands (leeandco's Worker reads no D1 now). Four consumers keep the production database out of `zbc destroy`'s reach; leeandco's and qom's sit in a customer's Cloudflare account, reachable only with a minted token.

## The interface, from three implementations

| Implementation | Adds to `{accountId, databaseName}` → `{databaseName, databaseId}` |
|---|---|
| ceo `d1` (2026-07-19), zbc's `r2` renamed; copied by foothill-metabolic, then web | — |
| crux (2026-07-28), on foothill's helper | `statements`, `additiveColumns: string[]`; no destroy |
| leeandco (2026-08-13), from web's; qom's copy (2026-10-06), believing zbc had none, a day before main's `apiToken` | `apiToken`, errors naming the credential |
| railmid (2026-09-05), from its vendored `r2` | `locationHint` |
| ceo `cloudflare.d1Databases` (2026-10-09) | `migrate`; no id output, binds by name; no destroy |
| main `d1` (2026-09-08) | `apiToken`, `primaryLocationHint`, `statements`, structured `additiveColumns`, `ready` |

Both `d1` lineages, ceo's and railmid's, started from zbc's `r2`. All three paths name the database in config and create it only when none has exactly that name, as main does (`d1/index.ts:139-233`); that shape, the creation-only location hint (ceo's lineage dropped it) and the deleting destroy are `r2`'s (`r2/index.ts:65-69`, `:98-136` at `9f13268`): our design read back, not convergence. Only the id output is each lineage's own: D1 binds by id; `r2` emitted only `bucketName`.

Lookups differ: ceo's lineage reads one `per_page=1000` page, which D1 caps (`d1/index.ts:43-48`); main pages, and ceo's `d1Databases`, like wrangler, GETs the name.

railmid's module refuses schema, while crux's `additiveColumns` is ordered free-form SQL, so a backfill `UPDATE` can follow an `ADD COLUMN`. Main's entries are `{table, column, definition}` and run after every statement (`d1/index.ts:174-176`, `:214-230`), leaving no slot for a backfill or an index on an added column, like web's.

### Migrations, before the deploy — open

| Consumer (files) | Where it runs | Credential |
|---|---|---|
| cedarpad (39, drizzle-generated) | `deploy.sh`, before `zbc apply` | `sops exec-env` |
| railmid (11), ceo (1) | their `cloudflare` forks' `migrate` flag, before `wrangler deploy` | the deploy token |
| leeandco (12, one a guarded `DROP`), qom (1) | `with-client-d1-token.ts` by hand, qom's between by-name applies of database and Worker | a D1-only token per command, then deleted |
| web (7), foothill-metabolic (2), varnick (15) | by hand; varnick's not yet run | the operator's |

All eight use wrangler's migrator and `d1_migrations` ledger, four also run the directory locally, and all that state an order put it before the deploy, which the three automated steps abort on failure. varnick tests that no two files share a prefix, as wrangler "will pick one silently" (parallel branches wrote three `0005`s in a day); railmid's CI gate wants them consecutive from `0001`. railmid's and ceo's step is one design, which main's `cloudflare` would silently drop ([distribution-drift](./distribution-drift.md)); leeandco's wrapper mints a token because its step "is not an apply".

`statements` cannot carry these histories, which hold run-once data: cedarpad's `0004` sets every row's `workspace_id`, web's `0002` builds Clients from that day's rows, leeandco's `0011` drops a table. crux, the end-state model's source, starts its database over because additive DDL cannot remove a table, repoint a column or tighten one. Each production database already holds wrangler's ledger, so a runner with its own would replay the whole history: 39 files for cedarpad.

Main's `d1` has no directory key (`d1/index.ts:141-177`); turso's (`turso/index.ts:99-104`, `:172-193`) can skip a file silently ([turso](./turso.md)). d1's doc defers one to "after the deploy" (`d1/index.ts:164-165`), the previous survey's post-deploy hook, which no consumer asks for: leeandco migrates after a full apply only because nothing runs between database and Worker. Main advises a placeholder `database_id` (`plugin/skills/zbc/wiring.md:53-58`, `d1/registry.json:12`) that "is never read" (`d1/index.ts:17-18`), but wrangler's d1 commands use a present id verbatim, looking the name up only when it is absent. railmid migrates against the generated config; ceo and qom declare the binding by name, which `bindings` still fills (`cloudflare/index.ts:450`).

### A database `zbc destroy` must not reach — open

crux defines no destroy so deleting its corpus is never "a side effect of `zbc destroy`". ceo made `d1Databases` forward-only because `d1`'s destroy deletes. leeandco's and qom's destroy reads only `CLOUDFLARE_API_TOKEN`, so finds nothing in the client account, deletion being "a deliberate human act". railmid dissents, keeping `r2`'s deleting destroy; to it, quietly leaving rows behind is "the worse outcome". Every surveyed `d1` instance is production-only, none ephemeral; cedarpad's preview shares production's databases.

Main's `d1` destroy deletes (`d1/index.ts:239-262`), as turso's does (`turso/index.ts:200-212`); `zbc destroy <env>` runs every module's destroy unconfirmed (`engine/destroy.ts:53-58`, `commands/destroy.ts:24-40`), and `ephemeral` is the only instance option (`types.ts:263-278`). A full-environment destroy applies imports on demand (`engine/destroy.ts:64-87`), so main's `d1` would resolve the minted `apiToken` and delete the client-account databases leeandco's and qom's modules cannot reach; games runs it, unmodified, in production now. `zbc update`, which every copy-mode apply recommends (`utils/vendor-stamp.ts:124-134`), swaps all six `d1`s of ceo's lineage for main's, destroy included (`utils/copy-refresh.ts:158-181`), silently for leeandco, qom and web ([distribution-drift](./distribution-drift.md)).

The DELETE's catch logs any failure as "skipped" and the run reports success (`d1/index.ts:251-262`; [engine-undeclared-state](./engine-undeclared-state.md)'s to fix), so under `ephemeral: true` the next apply would reuse the old database (`engine/apply.ts:100-123`).

### An imported token's error — open

leeandco and qom rewrote the 10000 hint to name the importing instance and its file. Main's names `CLOUDFLARE_API_TOKEN` and the personal-token page even for an imported token (`d1/index.ts:27-34`), replacing Cloudflare's own text whether or not `apiToken` is set (`cloudflare-api/index.ts:219-228`), and asks for "D1: Edit", though a `D1 Write`-only token was refused on a list, leeandco's first call and main's (`:186`; measured 2026-08-14), and main's `apiToken` doc asks for D1 Read and Write (`d1/index.ts:147-149`). r2 and cloudflare-email have the same fixed hint ([r2](./r2.md), [cloudflare-email](./cloudflare-email.md)).

## What it takes upstream

1. **Migrations, in `packages/cli/templates/infra/modules/d1/`:** a directory key applied where `statements` runs: after the database resolves, before any importing Worker deploys, on d1's own credential, with no engine hook, in wrangler's format and ledger. Open: shell out to `wrangler d1 migrations apply --remote` against a generated config (d1 has no wrangler dependency, `d1/registry.json:5-8`), or reimplement the ledger over `/query`, which railmid declined as "a second migrator with its own bugs". railmid's and ceo's placement, a `migrate` flag between the patch and `wrangler deploy` (`cloudflare/index.ts:698-731`), is a per-resource-type key on `cloudflare`, which ADR-0014 (`:46-52`, `:83-85`) rejected for bindings. `build.command` has the deploy token but precedes the generated config (`cloudflare/index.ts:646-661`), so suits only a name-only declaration; no consumer used it. The placeholder advice becomes a name-only declaration.
2. **Destroy.** Open: an instance option that `zbc destroy` skips, refused with `ephemeral` (an engine change, covering turso too), or a `d1` key making `destroy` a no-op or a refusal (d1 only).
3. **The 10000 hint as a function of `config.apiToken`**, naming the importing instance and asking for D1 Read and D1 Write.
4. **An ordered free-form list beside or instead of `additiveColumns`**, for a backfill: only a legacy-shaped database needs one (crux's held "one identity and no Workstreams" by 2026-09-03), a second `d1` instance on the same database, importing the first, serves today; item 1 subsumes it.

The bar question is whether companies that are not Zabaca share what items 1–3 rest on: a migration history in wrangler's ledger, data a teardown must not delete, a credential outside `secrets.yaml`. The per-command token wrapper, which nothing on main matches, and the mint-only root at rest are leeandco's and qom's own client-account policy.

Operator acts on a D1 database (leeandco, qom, varnick, crux, web) are [engine-verbs](./engine-verbs.md)'s.
