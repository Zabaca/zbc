# r2 — upgrade

**Consumers:** leeandco, railmid, ceo, agent-lab  ·  **Deployed in production by:** leeandco, railmid, ceo, agent-lab

## What they needed

Three things, each built once and independently. leeandco needs a credential
other than the environment's `CLOUDFLARE_API_TOKEN`, which is Zabaca's: its mail
bucket must sit in the client's Cloudflare account with the Worker that binds
it, since an R2 binding cannot cross accounts. agent-lab works around the same
fixed name. railmid's ADR 21 bounds how long `railmid-tapes` keeps match
recordings, each holding two players' handles and a chat log, with a bucket
rule rather than a dashboard setting. ceo wanted a bucket that exists before
the deploy that binds it, and that removing it from config never deletes.
Main's `r2` reads only `CLOUDFLARE_API_TOKEN` and has no lifecycle key
(`r2/index.ts:33-43`, `:48`), so the first two are open. The third is closed:
[ADR-0016 (zone and
Access)](../../adr/0016-zone-and-access-do-not-belong-in-the-deploying-module.md)
was written about ceo's fork and found it inlined by preference.

## The interface, from 3 implementations

### The credential — open

leeandco added an optional `apiToken: { from, output }`, falling back to the
secret, fed by a `cloudflare-token` that mints per apply from the client's root,
which main's `rootTokenSecret` also allows. The reason is one client's; the
shape is main's: five Cloudflare modules take the key, and `cloudflare-api`
documents it as how every one takes its token
(`cloudflare-api/index.ts:249-251`). Besides `r2`, only
[cloudflare-email](./cloudflare-email.md) reads the fixed secret alone.

leeandco's `destroy` always uses secrets.yaml, a workaround for its older `src/`
([distribution-drift](./distribution-drift.md)) that it counts on to keep `zbc
destroy` off the client's bucket. Main's full-environment `zbc destroy` applies
the import when `ctx.output` asks (`engine/destroy.ts:64-87`), so a port shaped
like `d1`'s reaches that bucket, guarded only by R2's refusal to delete a
non-empty one, as every other `r2` instance is.

agent-lab, on an unedited `r2`, keeps a hand-narrowed token for its bucket at
rest under the fixed name. A reference would not free that name without
something to import: main's `cloudflare-token` reads a root on every apply
(`cloudflare-token/index.ts:242`), which agent-lab does not store
([cloudflare-token](./cloudflare-token.md)).

Whether leeandco's bucket exists is unverified: its first apply (2026-09-09)
failed with `10042 Please enable R2`, a dashboard-only fix (failing fast on it
is [cloudflare-token](./cloudflare-token.md)'s), and its `CLAUDE.md` still says
R2 is off while its cutover runbook says inbound mail has worked on the Worker
since that day.

### Lifecycle rules — open

railmid added one key to the vendored module:

```ts
lifecycle?: Array<{ id: string; prefix?: string; deleteAfterDays: number; enabled: boolean }>
// deleteAfterDays: integer > 0. enabled: defaults to true.
```

The API has no per-rule endpoint, so apply PUTs the whole set to
`/accounts/{a}/r2/buckets/{b}/lifecycle`; an absent key sends nothing, which
keeps railmid's sponsor artwork rule-free. The reason is railmid's; expiry is a
setting every R2 bucket has. railmid uses only deletion by age, not the
multipart-abort, storage-class or date conditions Cloudflare's rules also carry.
Open:

- **Whole set, silently.** A dashboard-only rule is replaced on the next apply
  and nothing reports it; `cloudflare-zone` reports undeclared records as drift
  (ADR-0016 (zone and Access):39).
- **Cloudflare's default rule**, which R2's docs say expires multipart uploads
  seven days after they start, is presumably dropped by the PUT; unverified, and
  harmless to railmid, whose Worker writes single puts.
- **`[]`** PUTs an empty set; railmid's 2026-09-05 check against the real token
  covered a one-rule PUT, not that.

The production Worker imports the bucket. railmid records no apply, but tags
only after a full `zbc apply production`, which throws on a refused PUT, and has
tagged `railmid-v0.4.0` (2026-09-06, announcing ninety-day tapes) through
`railmid-v0.9.4` (2026-10-09). The bucket's current rules are unverified.

### A bucket before the deploy, never deleted — closed on main

ceo's `cloudflare` fork grew `r2Buckets: string[]`, run in production CI: before
the deploy it POSTs each name, reads `10004` as already there, and never
deletes. ceo chose the key again on 2026-10-09, a month after ADR-0016, with
zbc's unedited `r2` in its own tree. Main covers both halves:

- **Ordering.** An imported `r2` instance is applied first, and `r2Bindings`
  carries its name into `wrangler.jsonc` (ADR-0016 (zone and Access):22, :26;
  `cloudflare/index.ts:507`).
- **Never deleting.** `apply` destroys only an `ephemeral` instance
  (`engine/apply.ts:148-156`), `zbc destroy` cannot reach a removed one
  ([engine-undeclared-state](./engine-undeclared-state.md)), and `r2` logs R2's
  refusal to delete a non-empty bucket (`r2/index.ts:80-105`). With no retain
  option, a deliberate `zbc destroy` does delete an empty one, which ceo's key
  never does; for a provider that does not refuse, see [d1](./d1.md).

Composition needs the import, which railmid's Worker has. leeandco's Worker and
ceo's `tour-guide` bind the name as a literal: leeandco's test says its copy
has no R2 binding resolver (it has), and ceo's fork has none. What a deploy does
with a binding to a missing bucket is unverified: ceo says it fails ("bucket not
found"), leeandco's test that Cloudflare creates the bucket, main's `r2` header
that wrangler prompts (`r2/index.ts:9-10`).

## What it takes upstream

1. **`apiToken` on `r2`**, in `packages/cli/templates/infra/modules/r2/`:
   - the optional key, resolved by one helper for `apply` and `destroy` as
     `d1`'s `apiTokenFor` is (`d1/index.ts:125-137`), and a destroy comment
     saying a full `zbc destroy` reaches the bucket;
   - leeandco's 10000 hint for the referenced path, which names the minting
     instance and both permission groups; main's, like `d1`'s, points at
     secrets.yaml and the dashboard (`r2/index.ts:22-29`, `d1/index.ts:27-34`);
   - `registry.json` instructions for a `cloudflare-token` holding `Workers R2
     Storage Read` as well as `Write`, as leeandco's does and `d1` asks for D1
     (`d1/index.ts:147-149`), since the module lists before it creates;
   - tests modelled on `d1`'s (`d1/index.test.ts:314-367`), and the catalog row
     (`packages/cli/plugin/skills/zbc/modules.md:25`).

   No readiness work: main's `cloudflare-token` probes R2 read on the endpoint
   `r2` lists first, which leeandco probes by hand
   (`cloudflare-token/index.ts:146`, `r2/index.ts:49-57`).
   Until this lands, a copy-mode `zbc update` overwrites leeandco's fork
   (`utils/copy-refresh.ts:6-13`).
2. **`lifecycle` on `r2`.** railmid's diff against `9f13268` is the patch: the
   schema key, `lifecycleBody`, one PUT, the registry text and a test file, to
   be lifted by hand ([distribution-drift](./distribution-drift.md)). A port has
   to answer the three open questions above.
3. **Pre-deploy creation.** Nothing.
