# host-modules — new

**Consumers:** foundry, claude-mitm-proxy, cedarpad (three lineages, no shared code)  ·  **Deployed in production by:** foundry (its one environment, `ryzen-9`, is the box) and claude-mitm-proxy (by installers outside zbc); cedarpad's hatch runs in its `workspace` environment, whose guest serves production's `default` workspace

## What they needed

zbc's host family, promoted from foundry, converges the apply host and, through a digest-gated root script, an incus guest or ssh host. Only foundry (41 instance files) and cedarpad (four `vm-provision` instances) apply it. Two needs recur and are open on main: owning part of a file another writer changes, and confirming the running process took a change. A service on another machine recurs too, but main reaches one as root, leaving claude-mitm-proxy's non-root, launchd case. The rest is one consumer each. Nothing here has closed since the 2026-09-02 run (`single-consumer-modules.md`, `4b80c2e`).

## The interface, from 8 implementations in 3 consumers

### Part of a file — foundry, claude-mitm-proxy

foundry's `claude-settings` and claude-mitm-proxy's `edit_json` share four rules: read the document, change only owned entries and write the rest back; refuse an unparseable file; mark or name owned entries so they can be removed; and keep what another writer set, as in env files claude-mitm-proxy's fleet edits live. foundry owns each `hooks` entry but other declared keys whole, so a declared `env` replaces the object, a key it stops declaring stays, and it says it cannot yet declare `claude-mem`'s `enabledPlugins` switch, which claude-mitm-proxy sets. claude-mitm-proxy owns entries a level down (`env.<KEY>`, `enabledPlugins[<plugin>]`), merges `NO_PROXY` as a union, deletes its keys by name on uninstall except `DO_NOT_TRACK` and the `NO_PROXY` pair, and writes through a temporary file and a rename; foundry writes in place.

They collide in ryzen-9's `~/.claude/settings.json`, whose `env` holds foundry's one key and claude-mitm-proxy's five, and foundry's next apply deletes the five, including the placeholder credential claude-mitm-proxy's ADR-0024 put there for nested `claude` processes. Neither repo's one-writer rule can see the other repo.

On main, `host-file` rewrites the whole file whenever the bytes differ (`host-file/index.ts:13-23,31-40`), nothing merges entries, and zbc writes Claude Code settings only as `zbc init`'s skip-if-exists `.claude/` files (`src/commands/init.ts:174-178`).

### The running process — foundry, cedarpad

In all three the file converged, not the process reading it, unseen by file comparison or digest; each acts and checks differently:

- Prometheus's config is bind-mounted, so `up -d` saw nothing to recreate, and two new alerts missed the stall they were written for. `prometheus-reload` reloads through the API and checks Prometheus's own last-reload gauge.
- An `Environment=` drop-in reaches a runner only on restart, so `github-runner` checks the Listener's `/proc/<pid>/environ` and restarts it once idle.
- cedarpad's guest bridge serves old code from memory. `deploy-vm.sh` kills the dev stack after apply and checks only the build stamp on disk; `ws-service` warns that applying it kills the canvas.

On main, `docker-compose-stack` runs `up -d` (`docker-compose-stack/index.ts:18-28`), and `systemd-unit` restarts, unguarded, only when the unit's own text changed, else only starts it (`systemd-unit/index.ts:34,58-59`). `host-file` and the plugin catalog say `changed` exists so an importer can restart (`host-file/index.ts:6-10`, `registry.json:9`; `plugin/skills/zbc/modules.md:63-64`), but neither module reads its context (`systemd-unit/index.ts:27`, `docker-compose-stack/index.ts:18`), so an imported change restarts nothing. foundry's `hardening` meets this live: a `RemainAfterExit` oneshot documented to rerun every apply, it imports the `hardening-script` `host-file`, but its unit is unchanged since 2026-08-03, so a script edit alone does not rerun it.

### A service on another machine — claude-mitm-proxy, foundry

claude-mitm-proxy's installers work over ssh as a non-root user, on ryzen-9 (the fleet's only proxy) and mac-studio: a launchd LaunchAgent on macOS, a systemd user unit with linger on Linux, a binary compiled on the operator's machine, packages without root. They replaced foundry's `systemd-unit` instances on ryzen-9 for one way onto every host, needing only `openssl` there (ADR-0005); foundry runs the substrate, not the services. Their host-side far half, `remote/lib.sh` (services, rc hooks, stdin secrets, JSON edits, periodic jobs), is shared; the operator half is not, since the four installers resolve targets and deliver secrets differently (ADR-0017). `github-runner`'s units live in a CI guest no `systemd-unit` instance reaches, so GitHub's `svc.sh` writes them and foundry adds two drop-ins. Both send secrets on stdin; they differ on transport (ssh or `incus exec`), init system, who writes the unit, and privilege.

On main, `systemd-unit` writes only on the applying machine (`systemd-unit/index.ts:28-31`). `remote-provision` pipes a script to `ssh … bash -s` as `root` by default (`remote-provision/index.ts:69,146-158`), with `PROVISION_HOME=/home/<user>` (`:140`), a marker under `/var/lib/zbc-provision` (`provision-core/index.ts:13,150-152`), packages only through `apt-get` (`provision-core/index.ts:61-66`) and no file copy. Both provision modules send secrets down stdin (`provision-core/index.ts:54-59`), and a root script can write and start a system unit there; a non-root account, or launchd, is what main cannot serve. The installers' OAuth tokens come from the root `secrets.yaml`, which no module reads ([cli-gaps](./cli-gaps.md)); `FLEET_PROXY_TOKEN`, which zbc pushes to the fleet Worker, reaches a proxy only by installer.

### Compose over ssh — claude-mitm-proxy

The fleet's memory server, in production, is a compose stack on ryzen-9. foundry's three local stacks use the built-in with `dir` alone. Both write a 0600 env file before `up` and never remove data; only claude-mitm-proxy needed a project name, env-file path, override file, `--build`, `--remove-orphans`, source checkout and remote host. On main, `docker-compose-stack` takes `dir` and `services` (`docker-compose-stack/index.ts:11-16`), runs on the apply host (`:20`) and has no `destroy`.

## What it takes upstream

**The bar is in question for most of this case.** Every implementation, and both appliers of main's host family, run on or against ryzen-9. foundry is that box's repo, "Zabaca's self-hosted VM runtime" (foundry ADR-0028), and keeps `github-runner`, `apt-packages` and `git-worktree` out of zbc-core on purpose (foundry `CLAUDE.md:197-200`).

1. **Part of a document.** A sibling of `host-file`, or a mode on it, on the four rules: entries owned one level into a container, by a marker or by name, and an atomic write. `KEY=value` env files follow the same rule. Open: removing a key no longer declared. Both JSON uses are Claude Code settings on Zabaca machines; the primitive is generic, a `claude-settings` module would not be.
2. **The running process.** The smallest change: `systemd-unit` and `docker-compose-stack` restart on an imported `changed: true`, as `hardening` needs, and can defer one that would kill work in flight (claude-mitm-proxy's terminal spares children via `KillMode=process`). A file zbc did not write needs a per-service probe, so `prometheus-reload` would be a module for one service. cedarpad needs nothing: its kill fits as a guarded last step of `ws-app`, a forced `vm-provision` whose root script runs in the guest every apply (`vm-provision/index.ts:93,141,175`) under `set -euo pipefail` (`provision-core/index.ts:52`); `ce23e34` gives no reason for keeping it outside.
3. **A service on another machine.** `systemd-unit` gains an ssh target at user scope with linger, and a launchd counterpart; `remote-provision`'s root and Linux assumptions above become config, and it gains a file copy. Only `github-runner` needs a drop-in; the memory caps both consumers set already fit in `systemd-unit`'s `content`.
4. **Compose over ssh.** `docker-compose-stack` gains `project`, `envFile`, `files`, `build` and `removeOrphans`, with the transport from (3); any `destroy` runs `down` without `-v`.
5. **`github-runner`**: foundry's config (`repo`, `runnerName`, `installDir`, `workDir`, `count`, `labels`, `memoryHigh`, `memoryMax`, `patSecretKey`, `instance`, `user`; output `runners[]`), plus a deregistering `destroy` ([engine-undeclared-state](./engine-undeclared-state.md)), idempotence that asks GitHub, not just `.runner`, whose string match reads a renamed repo as converged (likely `gh-runner-games`, whose runners serve Zabaca/railmid; unverified inside the guest), the token off `config.sh`'s argv, and `ctx.secret`. Guest mode needs incus and `findVmOutputs` (`vm-provision/index.ts:56`). Runners are generic but this one is tied to one box's guests; zbc's own workflow points a fleet without such a box to an apt step on a hosted runner (`publish-npm.yml:100-104`).
6. **`apt-packages`**: config `packages`, `updateTimeoutMs`, `installTimeoutMs`; outputs `packages`, `installed`, `changed`; no `destroy`, since `apt-get remove` takes reverse dependencies; no apt sources, which a rebuilt box needs; Debian and Ubuntu only.
7. **`git-worktree`**, written for agents sharing one checkout on one box.
