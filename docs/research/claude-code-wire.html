What each column actually is

The three SDK columns are not three products — they are three values of one option, options.systemPrompt, passed to the same query() call.

Interactive — you type claude in a terminal
Headless — claude -p "…"
SDK default — query({ prompt }), systemPrompt omitted
SDK preset — systemPrompt: { type: 'preset', preset: 'claude_code' }
SDK + excludeDynamic — …the same, plus excludeDynamicSections: true

Every cell shows its real value — no ditto marks — so a column reads top-to-bottom on its own. Varies flags rows where the five configurations disagree.

Two units, deliberately. Everything labelled chars counts the characters of prompt text itself — the text field of each block, with no JSON around it. Content-Length is the only figure in bytes, and it measures the whole serialized request: that same text, plus 11–13 tool schemas, plus the JSON envelope. They are not comparable, which is the point of showing both — SDK default's 146 characters of system prompt still ride inside a 74,243-byte request.

CLI vs SDK is seven differences, not one

Block 1's identity line is the most quotable, but interactive and SDK-preset also differ in User-Agent, two beta flags, cc_entrypoint/cch, block 3 (+1,271), the role: system message (+2,058), and two tools. Only block 2 is byte-identical.

Headless is the odd one on thinking

display: "omitted" appears in -p only. Interactive and all three SDK configurations send bare {type: adaptive}. I earlier framed this as interactive dropping the field — it is headless adding it.

Going off first-party disables deferred tool loading — in both clients

Columns three and five point ANTHROPIC_BASE_URL at a local sink instead of api.anthropic.com — one CLI, one SDK. The credential never left the machine; the runs 401, but the requests are fully formed by then.

Both proxied columns confirm it, so this is base-URL-driven, not client-driven — the CLI and the SDK behave identically once off first-party:

The 17 tools that were deferred behind ToolSearch — Cron*, Task*, WebFetch, WebSearch, Monitor, SendMessage and the rest — all ship eagerly instead, and the two proxied tool sets are identical to each other. The role: system message shrinks to match, because the deferred-tool roster it carried has nothing left to announce.

Three other things go with it: the system blocks collapse (2 and 3 merge), scope: "global" disappears so cross-session cached prefixes are first-party-only, and two beta flags drop (advanced-tool-use, cache-diagnosis). The irony is worth naming: SDK default proxied has the smallest system prompt of any column (135 chars) and the second-largest request body — 76% of it tool schemas. Turning the prompt off saves nothing next to losing deferred loading.

Correction: # Doing tasks is not in the Opus 5 prompt at all

I had this row marked "present" across the Opus columns. It is absent from every Opus 5 run — I carried the finding over from the Haiku output-style experiment without rechecking. The two models get structurally different core blocks:

Haiku   block[2] 10,676 chars — # System · # Doing tasks · # Executing actions with care · # Using your tools · # Tone and style
Opus 5  block[2]  1,210 chars — identity · security policy · # Harness

So the custom-output-style deletion documented in matrix 2 is a Haiku finding. The row stays in matrix 1 as a constant marked absent, rather than being dropped, because "it isn't there on Opus 5" is itself worth seeing.

The credential changes the request — it enables refusal fallbacks

Column six is the same query({ prompt }) as column three, same working directory, same account. The only change is authenticating with an explicit CLAUDE_CODE_OAUTH_TOKEN instead of the logged-in session credential. Three things move:

+ beta flag  server-side-fallback-2026-06-01
+ body field  fallbacks: [{ model: "claude-opus-4-8" }]

Everything else is byte-identical: the same 146-character system prompt, the same 11 tools, the same 12,396-character role: system message, the same account_uuid and device_id. Only session_id and the bearer token differ, as they would between any two runs.

What it buys: if Opus 5's safety classifiers decline the request, the API re-runs it on Opus 4.8 server-side and returns that answer, instead of handing back a stop_reason: "refusal" for you to handle. No other configuration in either matrix sends fallbacks — under the session credential a refusal is simply a refusal. That is a meaningful behavioural difference to inherit from a choice that looks purely like plumbing.

Replicated with a second, independently generated token to rule out something specific to how the first was provisioned. Both produce byte-identical requests — same 14 beta flags, same fallbacks array, same 74,285-byte body — differing only in session_id and cch, as any two runs would. The trigger is the kind of credential, not the individual token. The second column is therefore not shown separately; it would be a duplicate.

Correction, and it invalidates something I said earlier: I described cch as a config fingerprint. It is not. Three byte-identical runs — same token, same directory, same everything — produced 652f4, 9af34, b5d44. Across the whole capture it holds 36 distinct values in 36 calls and never repeats, and it differs both between the main call and the title-generation call of one session, and between two calls of a single turn. It is a per-request value carrying no configuration signal, so the fact that it changes between any two columns of the matrix means nothing. Its row is greyed out and excluded from Differences only for that reason.

Every capture above was a single-call turn. Forcing a turn that requires a tool call — so the harness makes a second /v1/messages request to continue — exposes a field that never appears otherwise, and settles what the other two actually mean.

FieldScopeEvidence
cc_versionStable config fingerprint 19 calls share .b89, 15 share .6cb. Tracks call kind (main vs title-generation) and tool/permission config — the --allowedTools Bash run got its own .190. This is the field that carries config signal.
cc_entrypointDelivery surface cli / sdk-cli / sdk-ts. Stable and meaningful.

Where it comes from, and how to turn it off

The claude binary is a 245 MB Bun single-file executable with its bundled JavaScript embedded as plain text. Searching the raw bytes for the literal x-anthropic-billing-header: cc_version= lands on the builder: 

function RYn(e, t, r) {
  if (su(process.env.CLAUDE_CODE_ATTRIBUTION_HEADER)) return "";   ← kill switch
  let n = `${VERSION}.${e}`,
      o = process.env.CLAUDE_CODE_ENTRYPOINT ?? "unknown",
      i = xn(),                                          provider
      s = i === "firstParty" && Yd() || i === "vertex" ? " cch=00000;" : "",
      l = kKn() ? ` cc_workload=${kKn()};` : "",
      c = _de(t) && !t.isMainSession ? " cc_is_subagent=true;" : "",

  return `x-anthropic-billing-header: cc_version=${n}; cc_entrypoint=${o};${s}${l}${c}${u}`

// Yd() — "are we talking to the real Anthropic API?"

Two ways to drop it, both verified on the wire

CLAUDE_CODE_ATTRIBUTION_HEADER=0 removes the entire header — system[] goes from [84, 62] to [62]. Block 0 simply isn't emitted.

Pointing ANTHROPIC_BASE_URL anywhere other than api.anthropic.com drops just cch and cc_prev_req (both gated on Yd()), leaving cc_version and cc_entrypoint — 84 chars becomes 74. Note Vertex still sends cch; Bedrock, Foundry, AWS, Google Cloud, Mantle and gateway do not.

Also worth knowing: cc_entrypoint is literally process.env.CLAUDE_CODE_ENTRYPOINT ?? "unknown". The surface labels this whole report keys on are an environment variable, not an intrinsic property — honest here because nothing overrode it, but settable.

The documentation names both fields, and it matches the measurements

Anthropic documents this block as carrying "the client version and a prompt fingerprint", and notes that before v2.1.181 it "included a per-request token on custom base URLs and Microsoft Foundry connections". That maps cleanly onto what the capture shows, and resolves which field is which:

FieldDocumented asMeasured behaviour
cc_versionclient version + prompt fingerprint Suffix is stable per configuration — 19 calls share .b89, 15 share .6cb, and --allowedTools produced its own .190. ✔ a fingerprint.
cchper-request token 36 distinct values in 36 calls, never repeated, changes between two calls of one turn, no config signal. ✔ per-request, not a hash.

I had guessed cch was the config hash and been wrong twice before measuring it properly. The fingerprint was always in the field next door.

Still unknown: how the per-request token's value is produced. The builder emits the literal " cch=00000;" and no capture ever carried 00000; I searched the raw bytes for every cch= (3 hits), every x-anthropic-billing-header (8 — the rest are the block-assembly code that tags this line cacheScope: null), and for five-hex generators. No substitution site in the plaintext bundle.

Do you need to disable it behind a gateway? On 2.1.181+, no

The documented reason to set CLAUDE_CODE_ATTRIBUTION_HEADER=0 is a gateway that caches on the request body: a token that changes every request would sit at the very front of that body and miss the cache every time. That applied before v2.1.181, when the per-request token was still sent on custom base URLs.

On 2.1.220 the client already omits it off first-party — the Yd() gate — so there is nothing volatile left to strip. Two proxied runs with identical configuration: 

run 1  x-anthropic-billing-header: cc_version=2.1.220.b89; cc_entrypoint=sdk-cli;
run 2  x-anthropic-billing-header: cc_version=2.1.220.b89; cc_entrypoint=sdk-cli;

block[0] byte-identical  true      system[] identical  true      tools[] identical  true

A body-keyed gateway cache sees a completely stable prefix. Set it to 0 only if you are on 2.1.180 or earlier, connecting to Microsoft Foundry directly, or you simply want the ~80 bytes and the client-version disclosure gone. And note the documentation's own caveat: on a direct connection to the Anthropic API, caching is unaffected either way — because this block is tagged cacheScope: null and never enters the cached prefix at all.

Two corrections

I called cch a config hash and said the cc_version suffix "tracks call type, not surface". Both were wrong, and in a way that swapped their roles: the stable config fingerprint is the cc_version suffix, while cch is per-call noise. And the suffix isn't only about call type — passing --allowedTools produced a distinct value at the same tool count.

The reason this took four attempts to get right: every earlier capture was one call per turn, so per-call and per-turn were indistinguishable, and cc_prev_req could not appear at all. A field that only exists on continuation calls is invisible until you capture a turn that has one.

Telling whether a fallback actually fired

Requesting fallbacks and using one are different events. The request says it is willing to fall back; only the response says whether it did. Three independent signals, all in the SSE stream:

SignalWhereNormal turnFallback served
Iteration typemessage_delta →
usage.iterations[].type		 "message""fallback_message"

from: {…}, to: {…}}

Prefer the iteration type as the primary check. The fallback content block marks a switch point, but a turn routed to the fallback model by sticky routing carries no block at all — usage.iterations still reports it.

What the 34 captured responses show

── across every /v1/messages response in the capture ──
iterations[].type    {"message": 34}          ← no fallback served, ever
stop_reason          {"end_turn": 34}
stop_details         {null: 34}               ← nothing was refused

So: the token runs requested fallbacks, and no request in this capture ever triggered one. That is the expected result — nothing here was refusal-adjacent, and I did not try to provoke a refusal to demonstrate the path.

A capture gotcha worth knowing

Responses arrive Content-Encoding: gzip, and a proxy addon that tees raw stream chunks writes those bytes compressed. Grepping the saved streams for fallback finds nothing whether or not a fallback occurred — you have to gzip.decompress first. Worth checking before concluding a signal is absent.

A custom style is the only configuration that removes anything

Built-in styles are purely additive — block 3 grows, block 2 gains one rewritten sentence, nothing is deleted anywhere. A custom style does all that and strikes the entire # Doing tasks section from block 2 in a single 3,321-character delete. Block 2 has exactly three states and never contains your style's text, so this is not something you configure — it follows from choosing "custom" at all. Restate what you need in your style body, which lands in block 3 verbatim.

Correction: tool schemas do differ between CLI and SDK

I previously said tool schemas never drift. Building this matrix showed Bash differing — 1,366 chars under the CLI against 1,353 under the SDK. The cause is cosmetic: the co-author line embeds the model label, and my session's variant string (Claude Opus 5 (1M context) vs Claude Opus 5) leaks into the tool description. Same 13-character artifact that accounts for the SDK-preset vs headless block-3 delta. Input schemas are identical everywhere — five properties, same names — so the substance of the claim holds, but "byte-identical" was wrong.

Method: HTTPS_PROXY plus a combined CA bundle (certifi + mitmproxy CA) against a native Mach-O claude binary, which honors NODE_EXTRA_CA_CERTS. A mitmproxy addon streamed SSE responses through untouched while teeing them to disk, so the client never stalled behind response buffering.

Sizes are characters, not tokens. Diff lines ending … are truncated for width; counts are exact and unabridged. Matrix one used claude-opus-5, matrix two claude-haiku-4-5 — compare rows within a matrix, never across them. One capture session against client 2.1.220; not a claim about other versions.
