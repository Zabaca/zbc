# A host merge is a push the host makes, where a deployment opts in

**Status:** proposed (2026-11-11). Reverses one clause of [ADR-0018](./0018-a-proposal-is-a-ref-and-merged-is-ancestry.md) — "The host never accepts. No merge endpoint, no fast-forward endpoint" — **only for a deployment that sets `WALGIT_MERGE`**. Everything else ADR-0018 decided stands, including its definition of Merged. Builds on [ADR-0021](./0021-a-scoped-token-opens-one-repository.md) (who may merge is who may push, and a `write` scoped token is that) and honours [ADR-0007](./0007-walgit-object-storage-holds-the-log.md): a merge is a WAL entry and an Index move like any push, and nothing here is state the log cannot hold. Leaves [ADR-0012](./0012-a-name-can-refuse-a-stranger.md) untouched, by refusing rather than bypassing it.

A deployment that sets `WALGIT_MERGE` answers `POST /_walgit/merge?repo=<name>`: merge a **source** ref into a **target** branch by **fast-forward** or **squash**, provided the target is still at the commit the caller **expected**. The host builds the result and pushes it into its own Cache over git's local transport, so the push's hooks judge, publish and announce it exactly as they would a client's push. With the flag unset the route does not exist (404), and walgit behaves exactly as it did.

## Why

ADR-0018 refused a merge endpoint for two reasons: it "puts the host's name on a write", and "the conflict it hits has nowhere to be resolved". Both were true for agentgit, whose users are agents with clones, and both are still the default. The request that reopens it (GitHub issue Zabaca/zbc#205) is a host serving people **with no checkout at all** — Fredrin hosting git for users with no GitHub account — who can already review a branch without one (the compare endpoint, `op=compare`) and then have no way to ship it short of cloning. For them a merge endpoint is the missing half of the review, and the conflict question has an honest answer: refuse it, name the paths, and let the conflict be resolved where git resolves them, in a clone.

## What was decided

- **Opt-in, per deployment, default off.** `WALGIT_MERGE=1`, read through `capabilitiesFrom` like every other flag, forwarded to the container through `CONTAINER_ENV`. Off, `POST /_walgit/merge` is the 404 every unserved path is, and no other route, hook or document changes. Also absent without an object store: a merge is a compare-and-swap on the Index, and there is none.
- **A merge is a push the host makes.** The result is built in a scratch repository that borrows the Cache's objects (`objects/info/alternates`), and pushed into the Cache with `git push` over the local transport — the path the admin seed already takes (`src/admin.ts`). So `pre-receive` and `reference-transaction` judge it as they judge any push: Signer Lists, Proposals, `WALGIT_APPEND_ONLY`, the size caps, the deletion tombstone, and the publish's compare-and-swap on `index.json`; and `post-receive` announces it, so a Watcher and the push webhook hear of it as of any push. Writing the Index directly would be a second push path, and a door around the rules a push is held to.
- **A compare-and-swap, required.** The caller names the full commit id the target is `expected` to stand at; there is no "merge onto whatever is there". It is checked against the Index first (409 `stale`, nothing written), and then held by git: the push carries `--force-with-lease=<target>:<expected>`, so receive-pack moves the ref only from that commit, and the publish refuses a ref the Index moved meanwhile. Of two merges racing for one target, exactly one lands; the other is a 409 (`stale`, or `contended` when it lost to a write still in flight).
- **Two methods, no true merge commit.** `fast-forward` moves the target to the source and refuses (409 `not-fast-forward`) when it is not one. `squash` writes one new commit whose only parent is the target and whose tree is git's three-way merge of target and source (`merge-tree --write-tree`), with the author the request names as both author and committer. A two-parent merge commit was left out because nobody asked for it, and it is the one method that would make the history the host wrote look like history a person wrote.
- **A conflict is a refusal, never a marker.** A squash whose three-way merge conflicts is a 409 listing the conflicted paths, and nothing is written. A source the target already contains is a 409 `up-to-date` rather than an empty commit.
- **A Signer List refuses a host merge, and says why.** On a claimed name a ref moves only by a push a listed key signed, and the host holds no key and makes no Push Certificate. The merge is refused (403 `signed`) before any work is done, with a message saying to merge in a clone and push it signed. `pre-receive` would refuse the host's unsigned push anyway; the early refusal is so the reason is the one a caller can act on. The host never signs on anyone's behalf.
- **Who may merge is who may push.** The route sits below the same credential gate a push does, and `scopeTargetOf` classifies it as a write: a `write` scoped token for the repository or the deployment credential may merge; a `read` token is 403, another repository's token is 403, no credential is 401. On a public deployment, where anyone may push an unclaimed name, anyone may merge one — the merge adds no reach a push did not already have.
- **Squash and "merged is ancestry".** ADR-0018's definition is unchanged: a Proposal is Merged when its tip is an ancestor of its target's tip. **A squash-merged Proposal therefore does not read as Merged** — its commits are not in the target's history, only their content is — and it stays open until the repository expires, as any unaccepted Proposal does. This is deliberate: "this content landed" is ambiguous the moment the target moves on, which is why ADR-0018 refused it, and recording a squash as a merge would be the first fact about a repository the log holds outside git objects and signatures. Merging a Proposal so that it reads as Merged is a `fast-forward`. In practice the two rarely meet: Proposals are how a stranger reaches a claimed name, and a claimed name refuses host merges altogether.
- **Provenance records what happened.** The ref move is recorded as an unsigned push, because it was one: no certificate stands behind it. A host merge does not claim a Signer it does not have.

## Why not the alternatives

- **Writing the ref and the Index directly.** Faster, and it would skip every rule a push is held to — the very property the admin seed was built to avoid. A push into the Cache costs a subprocess and one quarantine, and buys every existing rule for free, including rules added later.
- **A merge as an op of `/_walgit/browse`.** The compare lives there, and a merge reuses its conventions (`?repo=`, the file summary in the answer). But browse is a read: a `read` token may make one, and `WALGIT_WEB` decides whether it exists. A merge is neither, so it has its own path.
- **Merging onto whatever the target holds.** Simpler for a caller, and wrong for every caller that reviewed one state of the target and would ship onto another. `expected` makes the review and the merge refer to the same commit.
- **Recording a squash merge as Merged** — rejected above.

## Consequences

- A deployment that opts in has a write path that does not carry a client's push: every refusal it can meet is a push's, passed through as the hooks wrote it (422 `refused` for a size cap, append-only, a deletion).
- The per-source rate limits (`src/rate-limit.ts`) count `git-receive-pack` POSTs, and a merge is not one, so a merge is not counted against them. A merge uploads nothing from the caller; a deployment wanting to bound merges as such is a later decision.
- The answer carries the compare's file summary of the target before and after (`files`, `totals`, `truncated`), and no diff text. When the summary cannot be computed in time the merge still stands and the summary is `null`.
- With `WALGIT_MERGE` unset, nothing in this ADR is reachable.
