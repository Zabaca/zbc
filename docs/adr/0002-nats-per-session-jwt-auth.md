# NATS auth moves from a shared password to per-session, subject-scoped JWTs

The landing page authenticated to NATS with a **shared `app` password served to
every visitor** from `/api/nats-config`. PR #12 scoped that user to
`landing.cursors.>` and capped `max_payload`, but the credential was still public
by construction, never expired, and could not be revoked per session: anyone
could publish on any `landing.cursors.*` subject indefinitely. As NATS is
promoted from a cursor demo to the central event bus, a shared secret is not a
viable auth model.

We replace it with NATS **decentralized auth (NKeys + JWT)**. An operator signs
an account; the account's **signing key** signs short-lived **user JWTs**. The
landing Worker mints one per session; the browser connects with it and can do
nothing else. This supersedes the auth posture recorded in ADR-0001 (the move of
`nats-server` onto Cloudflare); the deployment topology from ADR-0001 is
unchanged.

## What changed

- `nats-server` runs in **operator/account mode** with a `MEMORY` resolver. The
  operator, SYS, and APP account JWTs are baked into the committed
  `nats-server.conf`; all three are public (only public keys, operator-signed).
  The container needs **no runtime secret**; the old `$NATS_PASSWORD` env is gone.
- `/api/nats-config` is deleted. `/api/nats-token` mints a **bearer user JWT**
  scoped to `landing.cursors.>` (publish and subscribe), expiring in 5 minutes,
  restricted to `WEBSOCKET` connections. The client connects with
  `jwtAuthenticator(() => jwt)` and refreshes ahead of expiry so nats.ws's
  automatic reconnect always reaches for a fresh token.
- The only secret is the APP account **signing-key seed**
  (`NATS_ACCOUNT_SIGNING_SEED`), held by the landing Worker and never sent to the
  client. It is generated by `packages/nats-server/scripts/gen-nats-identities.ts`
  and stored (SOPS+age) in each environment's `secrets.yaml`.

## Considered options

- **Bearer vs. seed tokens.** `jwtAuthenticator(jwt, seed)` normally needs a user
  NKey seed so the client can sign the server's nonce. We set `bearer_token: true`
  on the user JWT, so the client needs no key material and the Worker returns just
  `{ url, jwt }`. Justified: the token is already short-lived and narrowly scoped,
  so the extra proof-of-possession a user seed would add buys little against a
  5-minute, single-subject-prefix bearer token. Chosen for its far smaller client
  surface.
- **Identity key vs. signing key.** The Worker signs with a dedicated account
  **signing key**, not the account identity key. `iss` is the signing key and
  `issuer_account` names the account. The operator and account identity seeds stay
  offline, so a leaked Worker secret is rotated by swapping the signing key in the
  account JWT and redeploying, without minting a new account.
- **Minting in the Worker vs. auth callout.** We mint in the Worker. The
  Ed25519/NKey signing was the flagged risk (some NATS JWT tooling assumes Node);
  `nkeys.js` is pure JS (tweetnacl) and verified working in the Workers runtime
  (`nodejs_compat` for Buffer). Auth callout (NATS 2.10+) is more moving parts and
  only pays off once authz turns dynamic, so it is deferred.
- **Preview account.** Preview landing talks to the **production** NATS server, so
  it reuses production's account and signing key (same `NATS_ACCOUNT_SIGNING_SEED`
  in both `secrets.yaml` files) rather than getting its own account.

## Consequences

- Rotation is a coordinated redeploy: regenerate identities, paste the new
  operator/account block into `nats-server.conf`, replace
  `NATS_ACCOUNT_SIGNING_SEED` in both environments, and deploy `nats` and
  `landing` together. The operator and account identity seeds are intentionally
  not persisted; regeneration produces a fresh set, which is itself the rotation.
- The token is scoped to the whole `landing.cursors.>` prefix, so any holder can
  still publish on any `landing.cursors.*` subject within its 5-minute life. The
  client therefore keeps deriving peer identity from the message **subject**, never
  a payload field; that defense stays load-bearing (see `app/live-cursors.tsx`).
  Per-subject-per-user scoping is a possible future tightening, out of scope here.
- `MEMORY` resolver means account changes require a config redeploy. Acceptable:
  the account set is static and baked into the container image.
