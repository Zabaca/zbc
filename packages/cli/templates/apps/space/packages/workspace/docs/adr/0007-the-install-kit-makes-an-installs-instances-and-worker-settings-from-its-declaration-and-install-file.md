# The install kit makes an install's instances and Worker settings from its declaration and install file

Status: accepted. Follows ADRs 0004 to 0006: the switches, the addresses and the mailboxes are the declaration's; this is where an install's names and deploy come from.

## What changed, and why

An install's deploy was eleven hand-written zbc instance files and a hand-kept `wrangler.jsonc` in the space package, with the install's account, store names, Access application and policy names, token names and secrets written into each, and copies of declaration values (the mailboxes, the push address) kept in the settings and pinned equal by tests. A second install would have meant copying all of it. Now one function turns a pair of files into everything:

- **The install file** (`workspace-install.json`, JSON beside the declaration, for the reason the declaration is JSON: zbc loads every `.ts` file of an environment's folder as an instance). It names the account, the Worker, every store, bucket, queue and database, the Access applications and policies, the machine doors' token names, the Realtime ids, the rate-limit namespaces and the secrets-store names of the secrets. An existing install's file carries the names it already had, exactly. `parseInstallFile` reads it against the declaration: a feature on needs its names, a name for a feature that is off is refused, each machine door has a token of its own, every business mailbox's sending domain has a delivery-report subscription. The token names moved here from the declaration (`agent`, `telegram` and `clientsDoor` keep only their paths; ADR 0002's rule that each machine has a token and path of its own is now this check and the declaration's path check).
- **The kit** (`kit`): `buildSpaceInstall(declaration, installFile, sopsNames)` returns the zbc instances (the Access applications for the host, Forms and the three guest paths, the machine doors, the raw-mail bucket, the delivery-report queue, the Worker with its secrets and vars) and `spaceWorkerSettings` the Worker's settings. An environment's instance files are one line each, exporting from the kit. Instance names are zbc's state keys and are constants of the kit, never an install's.
- **The Worker's settings are written by the build.** The space package's `vite.config.ts` reads the declaration, the install file and the content file, writes `wrangler.json` (gitignored) and hands that to the Cloudflare plugin, which produces `dist/space/wrangler.json`, the file the deploy ships. A file and not the plugin's inline `config`: with no config file the plugin starts from wrangler's defaults for a Worker with none (Workers Logs on, a build watch directory, an empty `define`), which would deploy settings nobody wrote. Read from a file the output is the old one, key for key. The hand-kept `wrangler.jsonc` is deleted; there is no second copy.
- **The vars that were copies are the kit's output.** `INBOX_MAILBOXES`, `INBOX_JMAP_MAILBOXES` and `CALENDAR_PUSH_URL` are written from the declaration (the Cloudflare mailboxes, the hosted mailboxes, the push host and the calendar's path); the Worker's code still reads them as vars. Reading the declaration directly and dropping the vars is possible and was not done: the inbox's whole test harness injects the lists as vars.
- **The build checks the three files against each other for any install.** The declaration parses, the install file fits it, and the content file is read with `readMailboxContent`, all at config load, so a pair that disagrees fails the build with every problem named and nothing is bundled. (ADR 0006's statement that the content file is checked at the build is this.)
- **An existing install's output is pinned.** A test in that install's own repo holds the eleven instances and the Worker's settings equal to what was written by hand before the kit (a fixture taken from the last hand-written deploy), and the kit's own tests hold that an invented company's pair makes a whole install with nothing of any other company in it.

## What does not change

The Worker is still named `space` (mail routing in other repos names it by literal), every store, bucket, queue, database and token keeps its name, and each store's object name stays a constant of its part, so no install's store is ever renamed. Applying is still by hand (`bunx @zabaca/zbc apply <env> space`), and a change to the code or to either file reaches the space only by that apply.
