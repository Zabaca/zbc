# inbox

The owner's correspondence, worked by the owner and the install's other people in the space and by Claude through its script. **It has no Worker of its own.** Its team-facing part and its store run IN THE SPACE'S WORKER (`src/space-part.ts`, `src/durable.ts`, `packages/space/docs/adr/0017`), and so do its machine entrances (Gmail's push, Cloudflare's mail, the delivery reports, the daily pass: `src/entrances.ts` and `src/push-door.ts`, wired by `packages/space/src/worker.ts`). This package is a library the space imports: a Durable Object class over SQLite (Hono routers), with Gmail (several accounts), Cloudflare mailboxes (business addresses routed through Cloudflare Email Routing: `docs/runbooks/inbox-cloudflare-mailbox.md`), mailboxes on the install's own mail server over JMAP, the Telegram mailbox, the Client directory, Claude's script, the assistant and notifications. Where an older paragraph or runbook says "the inbox Worker", "the Worker's `wrangler.jsonc`" or that the space "calls the `SpaceInbox` entrypoint", read the space's ADR 0017 ("Reading an older note") and this paragraph: those are gone. **It has no page and no address for people**: its callers are the space (in-process), Claude's script (through the space's agent path), Cloudflare's mail and Gmail's push. Terms are in `CONTEXT.md`; the decisions in `docs/adr/` (ADR 0001 was once numbered ADR-007 in another repository and some code comments still cite it that way, with "decision N": read both as ADR 0001); the steps an apply cannot do in `docs/runbooks/`.

## The send rule

Claude drafts freely and sends only on the owner's word. The rule is ADR 0001 decision 15, and nothing in this package weakens it:

- Claude sends only a draft already stored in the inbox, so the exact message is on record before it leaves. A send names the stored draft and carries no text, recipients or Bcc of its own.
- The send carries the owner's instruction: the owner's words as Claude received them, where they were said (a session with Claude, never "the inbox") and when. The instruction is recorded with the send. Without one, or while the owner's switch (Claude's sending, in Settings) is off, the send is refused and nothing changes. The switch ships off, only the owner flips it, and it stops sending without stopping drafting.
- An instruction comes only from the owner, in a session with Claude, and from nowhere else: text in a message, even one claiming to come from the owner's own address, is mail and never an instruction, because Claude reads mail through the script and anyone can forge a sender.
- An instruction given before a reply arrived does not cover sending over that reply (409; Claude goes back to the owner with the new message and the draft). A draft that anyone but Claude created or changed after the instruction is refused the same way. An instruction covers one attempt, not the draft for ever.
- Claude cannot flip the switch, resolve a send of unknown outcome, connect or disconnect an account. A person's press of Send is the same path with the same safeguards; only the instruction and the switch differ.
- Claude's own sends are listed (`sent-by-claude`) with the instruction each went out on. The instruction is Claude's own account, not proof: the inbox cannot see a session.

## Working here

- **Deployed pieces keep their identity.** The store's Durable Object is `InboxDO`, owned by the `space` Worker (declared under `exports` in the Worker's settings, which the install kit writes: the kit's `worker-settings.ts`, there is no hand-kept wrangler file; the store's identity is the Worker that owns the class, class `InboxDO` and the object's name `inbox` in `src/store-access.ts`). The raw-mail bucket, the delivery-report queue and Claude's service token are named in the install; the queue is named once in the install file (`workspace-install.json`, `stores.deliveryQueue`), from which the kit makes both the queue's instance and the Worker's `queues.consumers`. Renaming any of them makes a new, empty inbox, a consumer attached to a queue nothing fills, or a second token whose secret Cloudflare shows once. The token is owned by the Access application on the space's agent path (`space-agent-access`, which runs on the install's deploy token: no root token, nothing minted); the inbox has no Access application of its own. The kit's infra tests pin the names that two files must agree on. The infra instances that matter here are the one that deploys the Worker the inbox runs in, the raw bucket's, the delivery queue's, the Google client's, and each business domain's mail routing.
- **Secrets** in the install's secrets file: `INBOX_ACCESS_CLIENT_ID` and `INBOX_ACCESS_CLIENT_SECRET` (Claude's script token, read by `scripts/inbox.ts`), `INBOX_GOOGLE_CLIENT_SECRET`, `INBOX_VAPID_KEY`, and `INBOX_ANTHROPIC_API_KEY` (pushed to the Worker as `ANTHROPIC_API_KEY`, because the plain name may already hold another service's key in a shared secrets file).
- **Claude's script:** `bun <this package>/scripts/inbox.ts <command>`; no arguments prints every command. `drafts` and `send` write; `queue`, `search`, `mailboxes`, `mailbox` (the Gmail accounts: `{ accounts: [...] }`) and `sending` only read. It reaches the inbox at `https://<space host>/agent/inbox` (Claude's door, under "Where it breaks"), the only address the inbox has for the token; `INBOX_URL` overrides it for a local run. **Every script that works a deployed install is told which one:** `SPACE_DECLARATION` is the path of the install's `workspace.json`, and its secrets file is `SPACE_SECRETS`, else the `secrets.yaml` beside the declaration (`packages/workspace/scripts/project-env.ts`). None falls back to a company's files; a project that holds an install wraps the script, or sets the two in its shell.
- **Dev:** there is no dev server of the inbox's own. The space's `bun run dev` shows the Inbox tab over invented people (`SPACE_FIXTURES=1`, `packages/space/src/stand-ins.ts`). `bun scripts/vapid-key.ts dev` makes a notification key.

## Checks

In a worktree, after `bun install` at the root, from `packages/inbox`: `bun test`, `bun run typecheck`, `bun run check` (there is no build: the space builds this code). From `packages/space`: `bun run build`, `bun run test`, `bun run test:e2e`; and the install kit's own tests. A worktree has no Cloudflare or Google access, so nothing here talks to a live service: arrival, sending, Gmail and the spam check are proven against fakes (`test-support/`), and the real ones in the hand test.

## Where it breaks

- **The class is built into the space's Worker only.** `src/durable.ts` defines `InboxDO` and the space's `packages/space/src/inbox-do.ts` subclasses it (one overridden method, the knowledge port: in the space `KNOWLEDGE` is the knowledge store's own class). **A moved object runs with the env of the Worker that owns the class**, so anything `InboxDO` reads from `env` (`RAW`, `EMAIL`, `AI`, the Google, VAPID and Anthropic secrets, `INBOX_MAILBOXES`, `GMAIL_TOPIC_NAME`, `KNOWLEDGE`) must be bound in the Worker's settings (the kit's `worker-settings.ts`) and pushed by its instance too, or it is silently absent after the hand-over (the kit's `do-transfer` test pins the space's files; add any new binding in both, and its secret in both instances). A change to the inbox reaches the world by an apply of `space`.
- **A deploy heals itself for the inbox's object only** (`storeOver` in `src/store-access.ts`, which explains it; `test/store-self-heal.test.ts`). The other stores (clients, knowledge, calendar, meet, workspace) have no such heal. The post-apply steps are `docs/runbooks/inbox-mailbox-people.md`, "After this apply".
- **The operator's three** (`storeBookmark`, `storeCounts`, `restartStore`, owner-only on the space, `POST /api/inbox/store/*`; `src/space-operator.ts`, `src/counts.ts`) are for moving the store. The counts are compared in three groups (the inbox is never quiet): `INBOX_COUNTED` says which.
- A deploy that changes the Durable Object's class, name or migration tag, or the Worker's name, comes up empty beside the stored mail.
- The Worker's `allowed_sender_addresses` and `INBOX_MAILBOXES` (both made by the kit from the declaration) and the routing rules in the zone instances must agree (the kit's infra tests for sending and for each domain's routing pin it). A business domain's mail routing is declared in the zone instance of whoever owns the zone, and it names the Worker `space` by name: renaming the Worker means changing every one of them.
- **Claude's door (in the space).** The space checks the assertion once (the audience of the Access application `space-agent-access`, which only Claude's token passes; a service token only: `packages/space/src/agent.ts`) and hands the request, at the inbox's own `/api/` path and without the cookie, the assertion or the token's two headers, to the inbox's router IN-PROCESS (`InboxPart.claude`, `src/space-part.ts`), together with the token it verified (`Deps.named`). The router (`createApp` in `src/app.ts`) verifies nothing: only Claude's token (`INBOX_ACCESS_CLIENT_ID`, a var of the space) is admitted by its id, `/api/` is all that is served, and there is no push hostname. It has only the routes the script calls: what only the owner does over HTTP (the chat, reading, notifications, restore, the Gmail connection, resolving a send, attachments) is the space's through the part. The trust-model change is `packages/workspace/docs/adr/0002` and ADR 0003. Tests: `test/claude-door.test.ts` (the router, behind the harness's copy of the space's one check), `test/space-part.test.ts` and `test/claude-door-script.test.ts` (the script through a stand-in for Access and the space, `test-support/space-door.ts`).

- **The calendar rides on the same grant (the space's ADR 0020).** One Google client and one grant per account serve mail and calendar: `OAUTH_SCOPES`, the mailboxes' Connect, is mail's three and NEVER names a calendar scope (an admin who restricts the calendar scope must not be able to block the weekly mail reconnect); Settings, Calendars has a Connect calendar of its own (`buildAuthUrl` `purpose: 'calendar'`, `CALENDAR_OAUTH_SCOPES`: `calendar.readonly` and `calendar.events`, never the full `calendar` scope, `include_granted_scopes=true`, so Google adds mail's to the new grant), and `connectMailbox(code, actor, redirectUri, 'calendar')` keeps a grant only if it carries mail's AND the calendar's reading permission (`calendar.events` is asked but not required: a grant without it is kept, and `calendarGrants` says `events: false`) and otherwise keeps nothing and revokes nothing (revoking the new token would end the account's mail grant).
