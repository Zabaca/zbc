# The Telegram bridge's door and store: deploy and hand test

Placeholders: `<env>` (the deploy environment of the space), `<bridge-env>` (the environment, and its secrets file, that deploys the bridge), `<space-host>` (for example `space.northfield.example`), `<owner>` (the install's owner).

What it adds to an install: a third mailbox kind in the inbox's store (**migration 16, store version 17, one-way**), a second machine path on the space (`/agent/telegram`, its own Access application and token), and a **bridge**, a program on a machine of the install's own that holds the owner's Telegram login and pushes the owner's chats into the inbox through that door. Why and how: ADR 0001 decision 27 (`../adr/0001-the-inbox-is-its-own-worker-over-gmail.md`), and the company layer's ADR 0002 (`../../../workspace/docs/adr/0002-one-service-token-comes-through-the-space-on-one-path-to-one-app.md`, amended). The wire the bridge speaks is `../../src/telegram/wire.ts` (a contract and a bounded parser). Everything below is run from the deploying machine with Cloudflare, sops and the bridge's host reachable; a build has no Cloudflare access, no Telegram login and no bridge host, and nothing in a build touched any of them.

The first part of this runbook is the first install (the order, then the hand tests). The "Upgrading" paragraphs among the hand tests say what an existing install does when a version adds a feature: each says the order of the two applies (the space and the bridge) and whether it needs a bookmark.

**Where the bridge runs is the install's choice** (a service on a host, a pod in a cluster). The hand tests say "stop the bridge", "start the bridge", "restart the bridge", "the bridge's log" and "reboot the machine that runs the bridge"; translate each to the way the bridge is run. A bridge deployed without its door entries (the two `TELEGRAM_DOOR_*` secrets below) is refused by its deploy: a blank entry is an error there, so there is no connect-and-push-nothing form of a deployed bridge. To keep the owner from seeing Telegram yet, leave the bridge stopped (see Rollback); Claude's script reads the conversations either way.

## Before anything: the bookmark

Migration 16 runs when the store's object next starts under the new code. It cannot be undone by an older build (an older build refuses a store at version 17). Take a bookmark and write it down:

```
bun scripts/inbox.ts bookmark
```

(from the inbox package). An undo is a build of this code with the migration list kept (never an older commit as it was) and, only if the store itself must go back, Settings, Restore to that bookmark.

## Order

1. **Merge and check the build** (`bun run test` and `bun run typecheck` in the inbox, space, workspace and bridge packages and the infra package).
2. **Apply the Access application and mint the token, once.** `bunx @zabaca/zbc apply <env> space-telegram-access`. The module creates the application on `<space-host>/agent/telegram` and, because the token "telegram bridge" does not exist, creates it and prints its id and secret **exactly once** (`── capture these now ──`). It runs on the environment's deploy token, which must hold "Access: Service Tokens Write"; a token made long ago may not. If the apply answers 403 for the token, mint a short-lived account token carrying that permission, apply with it, then delete it. Capture the secret into the bridge environment's sops in the same command and never print it:

   ```
   out=$(bunx @zabaca/zbc apply <env> space-telegram-access 2>&1)
   id=$(printf '%s\n' "$out" | sed -n 's/^ *CF_ACCESS_CLIENT_ID=//p')
   secret=$(printf '%s\n' "$out" | sed -n 's/^ *CF_ACCESS_CLIENT_SECRET=//p')
   [ -n "$id" ] && [ -n "$secret" ] && \
     printf '%s' "$id" | jq -Rs . | sops set --value-stdin <bridge-env secrets file> '["TELEGRAM_DOOR_CLIENT_ID"]' && \
     printf '%s' "$secret" | jq -Rs . | sops set --value-stdin <bridge-env secrets file> '["TELEGRAM_DOOR_CLIENT_SECRET"]'
   printf '%s\n' "$out" | grep -v 'CLIENT_SECRET'; unset out secret id
   ```

   If the apply succeeded but the capture did not (the secret is shown once), set `rotate: true` on the instance for one apply to mint a new secret and capture that, then set it back to `false`. Commit the bridge environment's secrets file (encrypted).
3. **Deploy the space** (it carries the inbox, the new migration and the two new vars `CF_ACCESS_AUD_TELEGRAM` and `TELEGRAM_ACCESS_CLIENT_ID`, both from `space-telegram-access`'s outputs): `bunx @zabaca/zbc apply <env> space`. Check `wrangler tail <worker>` shows `inbox: the store object started` and no error, and that the Inbox still opens and the counts have not moved (the migration rebuilds `mailbox`: the Gmail accounts and every business mailbox keep their rows).
4. **Check the door from the deploying machine** (no secret printed; the empty body is refused by the parser, so nothing is stored):

   ```
   id=$(sops -d --extract '["TELEGRAM_DOOR_CLIENT_ID"]' <bridge-env secrets file>)
   secret=$(sops -d --extract '["TELEGRAM_DOOR_CLIENT_SECRET"]' <bridge-env secrets file>)
   curl -s -o /dev/null -w '%{http_code}\n' -X POST https://<space-host>/agent/telegram/api/work -H 'content-type: application/json' -d '{}' -H "CF-Access-Client-Id: $id" -H "CF-Access-Client-Secret: $secret"   # 422: in, and the body refused
   curl -s -o /dev/null -w '%{http_code}\n' -X POST https://<space-host>/agent/telegram/api/work -d '{}'                                                                                          # 302 or 403: Access, no token
   unset id secret
   ```

   And Claude's token on the bridge's path is refused, and the bridge's on Claude's: with `INBOX_ACCESS_CLIENT_ID`/`_SECRET` from the environment's sops, the same request to `/agent/telegram/api/work` must not answer 200 or 422.
5. **Apply the bridge** (the bridge's deployment gets the door entries): apply the bridge's instance in `<bridge-env>`, then restart the bridge if only a sops entry changed (a Secret change does not restart it). With the entries filled the log shows `connected as Telegram user` and `telegram-bridge: live` (a missing `live` after 90 seconds means it is still filling or the space is not answering). With them blank the apply refuses, because a blank entry is an error there.

## Hand tests (only these prove the real Telegram; the build proved the rest against fakes)

Run in this order; each states what to compare. Never connect to Telegram from another machine with the bridge's login while the bridge runs.

1. **The first fill.** `bun scripts/inbox.ts telegram` shows `state: live`, `hasPosition: true`, and counts. Compare the count of messages in one-to-one chats over the last 30 days with the phone (the messages in groups are the groups' tests below, and Saved Messages and Telegram's service chat are not carried). `queue` shows the chats as rows with `kind: telegram` and the mailbox "Telegram"; each chat is read or unread as the phone has it, and archived chats are Closed.
2. **A message arrives within a second or two.** From a test account (or another person), send the owner one message; `queue unread` shows it. Send a second from the phone to someone: it appears as the owner's own, read.
3. **Idempotence, restart and a reboot of the bridge's machine.** Restart the bridge twice; `inbox.ts telegram` counts do not move, no conversation shows a message twice. Then **reboot the machine itself**, with one message sent to the owner while it is down: when it is back the bridge starts by itself, the log shows a catch-up (`catch-up step 1`) and not a fill, the missed message is stored once, and the counts are otherwise unchanged. Nothing is lost across a reboot because the position is the space's, not the machine's disk (nothing of a message is on it).
4. **Catch-up** (an open unknown of the first version): stop the bridge, receive three messages, edit one, delete one, wait an hour (or a few minutes to see the happy path), start it. The three are stored once, the edit shows `editedAt`, the deleted one shows no text and a `deletedAt`. The log says `catch-up step 1: ...`; if Telegram says the gap is too long, `read-through`.
4b. **A hole in the live updates.** On the bridge's machine, take the network down for about a minute while one message is sent to the owner from a second account, and one more right after it comes back. The log shows the connection returning and `live updates cannot be trusted past this point (reconnect)`, then a `catch-up step`; both messages are stored once, in order, and `inbox.ts telegram` counts agree with the phone. If the first is missing from the store, the position passed a hole: stop the bridge and report it.
5. **Names, phone join, bots.** A contact who is also a text contact with the same number is one person (check `contacts`), and Split undoes it; a bot's chat is under Bulk (`queue bulk`). The names shown are the names the owner saved the contacts under: if some are Telegram's own profile names, the `name` the bridge sends is not what was assumed (the server is believed to apply the saved name to the user object; this is read from GramJS's types, not from a live Telegram).
6. **The login code never arrives (an active check, not a wait).** With the bridge live, have the owner ask Telegram for a login code on a second device (open Telegram on another phone or on web.telegram.org and start signing in as them; do NOT enter the code, and expect Telegram to show a new-login notice in the Devices list that the owner then ends). Telegram writes the code into its service chat (777000) on the account within seconds, so it is the real thing the exclusion is for. Then confirm nothing from that chat is in the store: `inbox.ts search "login code"` and `inbox.ts search "Telegram"` find no message with a code, `inbox.ts contacts` shows no contact named Telegram or with a Telegram identity `777000`, and the bridge's log shows it staying live with no push for it. Repeat after a restart of the bridge (the catch-up path then sees the code message in Telegram's difference) and after a reboot of its machine. If anything from 777000 is in the store, stop the bridge first and tell the owner to end the new login in Devices.
7. **Offline status.** From a second account the owner shows as last seen, not online, while the bridge is connected (an open unknown; the bridge reports offline either way).
8. **The space down.** With the bridge live, a deploy of the space is a window in which pushes fail: the log says `trying again in Ns`, nothing is lost, and the counts catch up.
9. **Signed out.** Not to be tested on the real login. The path is covered by the bridge's tests (exit 78, status `signed-out` to the space); the card and the foot line for it are checked by the space's e2e over the fixtures (`telegram-signed-out`).

### Screens and notifications

No migration and no apply of its own beyond the deploy of the space: Telegram rows with one Telegram pill in the Inbox, a Telegram entry in the menu's Mailboxes (and Telegram's bot chat in Bulk, an archived chat in Closed), the history with edited and deleted messages, the Telegram card in Settings, Mailboxes, the menu's foot line (the same sentence on both), and notifications by the mail rule (tests 10 to 12). The bridge needs a re-apply (it marks live pushes and reads the chat list again for mutes).

10. **A live message rings, once.** With a Telegram notification device turned on in Settings, Notifications (the space's, on the owner's phone), have a test account send the owner one message in a one-to-one chat. The phone shows "Telegram: <name>" over "New Telegram message" (never the words), the tap opens that person in the space, and a second notification for the same message never comes. `inbox.ts telegram` and `notifiedSince` agree: one sent. A message sent from the owner's own phone or from a bot does not ring.
11. **Mute and catch-up do not ring.** Mute that chat in Telegram on the phone, wait over a minute (the bridge reads the chat list again when a live message arrives and the list it holds is a minute old), send another: no notification. Unmute and send: it rings. Then stop the bridge, send three messages, start it: the log says `catch-up step 1` and the three are stored but **no** notification comes (a catch-up and a first fill never ring, whatever their age). Restart the bridge with nothing new: nothing rings.
12. **The screens, on the real data.** In the space at 1440 and on a phone: the real rows (Telegram pill, one per person, archived chats under Closed, bots under Bulk), a person who writes by email and on Telegram is one conversation with both histories, the Telegram card in Settings, Mailboxes reads "Telegram is live, last message ..." with the counts of hand test 1, and the menu's foot has the same line. Stop the bridge for six minutes: the foot line and the card turn amber with a sentence saying the bridge has not checked in since the time; start it and they clear.

### Groups and channels

A second one-way migration (migration 17, store version 18): four nullable columns, no table made again. **Upgrading from a version without groups:** **bookmark** (again: the bookmark taken for migration 16 does not cover 17), merge, **apply `space`** (the inbox with the migration and the wider door), then **re-apply the bridge** (it starts pushing groups and channels; until the space is deployed the old door refuses a group in a push with a 422 and the bridge's batch is stuck, so the order matters). The bridge fills nothing again: it catches up from the stored position, then reads each group and channel that has no stored position of its own (tests 13 to 16). Rolling back is stopping the bridge as in Rollback below; the migration is not undone.

13. **Groups come in, once.** After the re-apply, `bun scripts/inbox.ts queue` shows each group as one conversation named by its title (`telegramChat: group`), with the last 30 days; compare the message and group counts with the phone. The log says `first fill` for none (a position is stored) and `read one group` / `group catch-up step` lines with counts. `inbox.ts contacts` lists the people who write in them and no contact named like a group; a person who also writes to the owner one-to-one is ONE contact (check by name).
14. **The group-addressing rule on the real thing.** From a second account, in a group the owner is in: (a) write an ordinary message: it is in the Inbox as an unread open row, no notification, not in Today's Needs reply; (b) write one that mentions the owner by @username: it rings once ("Telegram: <name> in <group>" over "New Telegram message"), the row shows Needs reply, and the tap opens the group's row; (c) reply to one of the OWNER'S messages in that group without mentioning them: it rings too (if it does not, Telegram did not mark it as addressed and the reply is known only through the stored message, so check that the message replied to is within the 30 days); (d) close the group in the space, then write ordinary messages: it stays closed; mention the owner: it reopens. A group the owner muted in Telegram never rings, even for a mention. If a mention does not ring, the `mentioned` flag is not what the build assumed (it is read from GramJS's types): the log shows the batch and `select telegram_to_me` in the store shows 0 for it.
15. **A channel.** A channel the owner follows is under Bulk (`queue bulk`), never the Inbox, Unread or Today, rings nothing, has no reply box, and is not in People. A post, an edit and a deletion in it arrive (the deletion names the channel); `inbox.ts telegram` counts them.
16. **Catch-up per channel.** Stop the bridge, have a supergroup and a channel receive three messages each, start it: the log says `group catch-up step 1` and `channel catch-up step 1` (each asked from its own position) and the six are stored once. Then the same with the bridge stopped for a day or more, if Telegram says the gap is too long (`a ... gap is too long ... reading it instead`). This answers the per-channel unknown of the first version for real.
17. **The space at 1440 and on a phone, on the real groups:** one row per group under its title (tag Group, the newest message named by who wrote it), no row for a member, the conversation headed "Telegram group" with each message named, a member's page listing the groups they write in and opening each, Settings's card reading as before.

### Read marks, both ways

No migration (the marks owed are `setting` rows, `telegram-read-owed:<chat id>`, so the bookmark for groups is the last one needed). It adds a fifth call to the bridge's door, `outcomes`, and the bridge's first writes to Telegram: `messages.ReadHistory` and `channels.ReadHistory`. **Upgrading:** apply `space` first (the door learns `reads` on `events`, and the owed list on `work` and `outcomes`), then re-apply the bridge. Either order is safe. A read made on the phone while the bridge is still the old one is lost to the space whichever order is used (the old bridge maps a read update to a position and drops the read). A new bridge on an old door sends `reads` the old door ignores (it still takes the position) and finds nothing owed, so it calls no `outcomes`. And a mark owed while the space is deployed first waits as a `setting` row and is made once the new bridge arrives. Nothing is owed until the owner opens a Telegram conversation in the space after the deploy, so the first hand test is safe to do on one test chat. Rolling back is the same as before (stop the bridge); a mark already owed is only ever a read mark and stays harmless.

18. **The phone reads, the space follows.** With an unread one-to-one message in the space, open that chat on the phone (or any device). Within a second or two the conversation is read in the space (no longer in `queue unread`; the row loses its dot and the menu count drops). Then the same for a group (basic and super) and, last, a channel: reading it on the phone clears it in the space. The bridge's log shows `live: ... 1 read mark(s)`.
19. **The space reads, the phone follows.** From a test account send the owner one message in a one-to-one chat; do NOT open it on the phone. Open that conversation in the space: the chat is read on the phone within a few seconds (no badge), and on the test account the message shows two ticks (the other person SEES it). The log says `read mark: a user chat marked read`. To see the debt itself, run `bun scripts/inbox.ts telegram` right after opening the conversation (the bridge asks every three seconds, so be quick, or stop the bridge first): it shows `readMarksOwed: 1` and `oldestReadMarkOwed` set. Start the bridge and run it again: `readMarksOwed: 0` and `oldestReadMarkOwed: null`, the outcome having settled it. A count that stays above 0 with the bridge running means the mark is not being made (the log says why, or the audit holds a `telegram.read-mark-failed` entry and the count drops to 0).
20. **Exactly what the owner saw.** The race (a message arriving after the page was drawn) is proved by the unit test, `test/telegram-readmarks.test.ts`, not by hand. By hand, check the plain case: the test account sends three messages, the owner opens the conversation in the space, and the phone shows it read; then the test account sends a fourth and the owner does NOT open the conversation: it stays unread on the phone (opening in the space marks read; a message arriving afterwards does not).
21. **A group, a supergroup and a channel each use their own call.** Do 19 for a basic group, a supergroup and a channel the owner follows (a channel is Bulk: find it with `queue bulk`). Each clears on the phone. If a supergroup or channel does not clear, the log's `read mark: Telegram did not take it (CODE)` names the code (it is Telegram's short answer, never text); `CHANNEL_PRIVATE` or `PEER_ID_INVALID` is reported as failed for good and `audit` holds a `telegram.read-mark-failed` entry.
22. **Claude reading marks nothing.** Have Claude read the same unread conversation through its script (`queue`, `conversation <id>`, `search`): it stays unread in the space AND on the phone. This is the rule that unread means the owner has not looked.
23. **No echo, no flicker.** Open a conversation in the space and watch the phone and the space for a minute: both stay read, nothing goes unread, and the log shows one read mark made and one `read mark(s)` heard back (Telegram tells every device, the bridge included, that the chat was read; the space ignores it as it is already read).

### Sending

No migration (the owed send is a `setting` row, `telegram-send:<message id>`, and a refusal's words `telegram-send-failed:<message id>`; the last bookmark needed was the groups'). The owner's Send in the space sends on Telegram as the owner, in a one-to-one chat or a group, through the bridge (a channel has no reply box); Claude's send is the existing instructed send (a stored draft, the owner's recorded instruction, the owner's switch on). The door still has five calls; `work` now offers sends and `outcomes` takes their results; the bridge's allow-list grows by `messages.SendMessage`. **Upgrading, order: re-apply the bridge FIRST, then apply `space`.** The reverse leaves a window in which the space offers a send to a bridge that skips what it does not know (it ignores `send` items and reports nothing): a send pressed in that window is offered for five minutes, never done, and then shown as "check Telegram" (nothing was sent, and the owner takes it back). The new bridge on the old space is harmless: the old space offers no sends and the bridge reports only what it was offered. No migration, so no bookmark is required, but take one anyway if the deploy also carries anything else (`bun scripts/inbox.ts bookmark`).

24. **Send, in a one-to-one chat (a test account first).** In the space, open the conversation with the test account, write a short message and press Send. The box says "Sending on Telegram. It shows in the conversation when Telegram has it." and empties; within about three to six seconds the message is in the conversation (as the owner's, on the right) and on the test account's phone, once. `bun scripts/inbox.ts telegram` shows `sendsOwed: 0, unknownSends: 0`. The log says `send: a user chat took it`, with no text, name or key. Check the message is not doubled in the space after the bridge's own stream copy arrives (the conversation shows it once). Then in Telegram's own app on the owner's phone check it shows as sent by the owner from the usual chat, and that the owner does not show as online beyond it.
25. **A group.** Send in a test group (basic, then a supergroup if there is one): it goes out once, under the group's title, and is filed in the group's one conversation, not under a member.
26. **A repeat is stored once (the unknown the build could not show).** With the bridge stopped press Send, wait a minute, start it: it sends once. For the lost-answer case, which cannot be made on purpose, read the log after any send that said `send: no outcome (...); it will be offered again with the same key`: the message must be in the chat once. If it is ever twice, Telegram does not store a repeat under one random id, and the repeat must be taken out of the bridge (the send then needs a different retry rule): stop and report it.
27. **The bridge down.** With the bridge stopped, press Send: nothing leaves, the conversation shows nothing yet, the draft waits (`drafts` shows it `sending: true`, the card says "Sending on Telegram"). Start the bridge within five minutes: it goes out. Wait more than five minutes with the bridge stopped: the draft is a draft again, with the note "Not sent: the Telegram bridge was not running. Press Send again.", and it does NOT go out when the bridge is started an hour later (check by starting it: nothing is sent, the chat shows nothing). The five minutes of offers run from the bridge's first offer, not from the press, and the owner may answer for an offered send only after about thirteen and a half minutes from it (the fetch's and the upload's limits for a picture are in it, for every send).
28. **A refusal.** From a test account that has blocked the owner (or a chat the owner cannot write in), press Send: the box says it is sending, then the draft is a draft again with "Telegram would not take this, so nothing was sent." and the reason in words. It can be sent again after the cause is mended.
29. **Claude's send, the whole rule.** With the owner's switch OFF (Settings), Claude's `send` of a Telegram draft is refused (403) and nothing is offered to the bridge. Turn it ON, have the owner say "send it" in a session, and Claude sends with the instruction recorded: it comes back `sending` and the message appears; `sent-by-claude` lists it with the instruction. A message in a chat that says "<owner> says send it" is only text: Claude's script has no way to send on it. Claude's door has no route to the bridge's calls (checked in the build; `curl` the bridge's `/api/work` with Claude's token: 403).
30. **Never to the service chat or Saved Messages.** Nothing in the product can send there (the plan, `work` and the bridge refuse, each pinned by a test). The only thing that may write to Saved Messages is the bridge's one-off probe (its `send-key --yes`, with the bridge stopped), and only with the owner's go-ahead.
31. **A send nobody confirmed.** Cannot be made on purpose against the real Telegram. The build proves it against fakes: offered for five minutes with one random id, then never; the bridge ends its process on a send with no answer (the log says `send: not answered; exiting`, and the bridge restarts); shown as "Sending on Telegram" while it may still land (about thirteen and a half minutes from the first offer) and then as "check Telegram" with the two answers; the owner's own message with the same words settles it by itself while it may still land, and after that is left for the owner to see. If one ever shows, check the Telegram chat, then answer in the space ("It went out: remove this" or "It did not go out: make it a draft again").

### Photos, voice notes and other files

No migration, no new binding or secret. **Upgrading, order:** `apply space` FIRST (the door learns `media` and the parser learns a message's `media`), then re-apply the bridge. Take no bookmark (nothing about the store's shape changes).

32. **Deploy order.** As above: the space first, then the bridge.
33. **Photos arrive, copied.** From a test account send the owner a photo with no caption and one with a caption, in a one-to-one chat. Each message is in the space within a second or two as "[Photo]" or its caption, and within a few seconds more (the bridge's three-second poll, then the download) a thumbnail appears under it (a click opens it full size in a new tab; the page never reloads). The log says `media: a photo of a user chat copied`, with no name or text. `bun scripts/inbox.ts conversation <id>` (Claude's script) shows the message and no file at all. Repeat in a group.
34. **A voice note plays.** Send a voice note from the test account. A player appears with "Voice note, 0:NN (size)" and a Save link. Play it in Chrome on a computer; then **in Safari on an iPhone**: this is an open unknown (Safari plays Opus in Ogg only from a recent version). If it plays, nothing more. If it does not, the page says "This browser could not play it here. Save it, or open it in Telegram." and the Save link works; report it and the file's first bytes (`OggS`), and the follow-up is converting voice notes in the bridge.
35. **What stays in Telegram says so.** Send a document (a PDF), a sticker and a GIF: each is a chip with its kind and size ("File (12.4 KB)") and the line "Not copied here. Open it in Telegram.", with nothing to click. Send a voice note over 10 MB if one can be made (a video over 50 MB is hand test 44): the line is "Too large to copy. Open it in Telegram." and nothing was downloaded (the log shows no `media:` line for it). Post in a channel the owner follows with a picture: named only.
36. **Files arriving after the deploy.** Photos and voice notes that arrive after the deploy are copied ten at a time (the work request offers ten and the bridge fetches one at a time), so a burst has all its thumbnails or players, or lines, within a few minutes. Photos stored before the deploy are copied by the repair of hand test 41. `select count(*) from setting where key like 'telegram-media-owed:%'` (through the operator's counts, or the bookmarked copy) falls to 0 after a burst. A message with "Copying from Telegram." for more than a few minutes means the bridge is not fetching: the log says why (`media: ... could not be copied yet (CODE), try N of 5`).
37. **Deleted for everyone takes the file.** Send a photo, wait for the thumbnail, delete it for everyone in Telegram: the message becomes "This message was deleted in Telegram." with no thumbnail, and its object is gone from the raw bucket (`wrangler r2 object get <bucket> tg/<message id>` is not found: the message id is in the audit entry or the store).
38. **No new Telegram session.** After the first downloads, open Telegram, Settings, Devices on the phone: no new entry beyond the bridge's own appears. A file stored in another data centre makes the library borrow a connection to it (it exports the login there); if a second entry shows up and stays, report it (it could end the login or look like a second device).
39. **The service chat and Saved Messages.** Nothing from Telegram's service chat is ever copied (a login code is text; there is no file in it), and a photo in Saved Messages is not carried at all: no `media:` line, no object under `tg/`.
40. **The bucket's growth.** After a week, list `tg/` in the raw bucket: the count is the photos and voice notes of the week, and the total is megabytes, not gigabytes. If it is not, stop and report: the limit or the channel rule is not holding.

### Images sent as files, and videos

No migration, no new Telegram call and no new call on the door. Photos and voice notes were once never copied at all because the bridge read every file as self-destructing (GramJS gives `null` for a field a message does not carry; a bridge asking for `undefined` sees every file as self-destructing), so the space held "[Photo]" and nothing else; the mapping is mended, a picture sent as a file (png, jpeg, webp, heic; not a gif) and a video (a player; up to 10 MB at first, up to 50 MB since the follow-up below) are copied too, and the messages stored without a file are given one by a one-time re-read of each chat's last 30 days (ADR 0001 decision 32, the follow-up). **Upgrading, order, strictly: apply `space` FIRST, then re-apply the bridge.** The old space refuses a push carrying the new kind `image` whole, which would end the new bridge until the space is deployed. The space first is harmless to the bridge that is running. Take no bookmark.

## What the build could not show (decide, or watch for)

- **GramJS shapes.** The bridge's mapping reads GramJS's objects as its types describe them (the bridge's `src/mapping.ts`, tested with objects of that shape): the dialog list (the archive is folder 1), a user's saved name and phone, `UpdateShortMessage` and `UpdateNewMessage`, `UpdateEditMessage`, `UpdateDeleteMessages`, `updates.getDifference`, and the entities GramJS attaches to a live update. A wrong guess shows as a chat or message missing, or a live message of a person not yet in the dialog list being left out (the bridge then reads the dialog list again once per 30 seconds and says `left out N message(s)`).
- **Mute.** `muted` is carried per chat from the dialog list with each push and used once, at the message's arrival, by the notification rule (never ring a muted chat); it is stored nowhere (so it needed no migration). The bridge reads the dialog list again when a live message from the other person arrives and the list it holds is a minute old, so a mute made since is at most a minute stale: one message may ring for a chat muted in the last minute.
- **Position bookkeeping on live updates.** The account's position moves with a live batch only along an unbroken line of `pts` (each update's `pts` is the last plus the positions it took); `updatesTooLong`, a connection that came back, an update that could not be read, an update that jumps ahead, or a one-to-one message nobody could name end the line and a catch-up from the stored position fetches the rest, because GramJS 2.26 fills no hole itself (its `catchUp` is a TODO). If the real Telegram's `pts` and `ptsCount` do not behave as the types say, the symptom is the log line `live updates cannot be trusted past this point (...)` on most batches, each followed by a catch-up (harmless, repeated work); the dangerous case, a hole not seen, is what hand test 4b is for.
- **Groups and channels.** Everything about them is read from GramJS's types and proven against fakes of that shape: the dialog list's channel entities and their `pts`, a message's `fromId`, `mentioned` and `replyTo`, `UpdateNewChannelMessage`, `UpdateEditChannelMessage`, `UpdateDeleteChannelMessages`, and `updates.getChannelDifference` (its `final` flag, the too-long answer). The assumption marked unchecked is that Telegram sets `mentioned` for a mention of the owner; a reply to one of the owner's messages is also decided by the inbox from its own copy, so only a reply to something older than the first fill rests on Telegram's flag. A supergroup's `Dialog.pts` is the position stored after a read; if the dialog list does not carry it for a chat, that chat has no stored position and is read again each start (cheap, and visible as `read one group`). A channel with the group's id spelling `-100...` is a supergroup or a broadcast channel by its entity (`megagroup` or `broadcast`); one the answer did not describe is left out until the dialog list does.
- **Read marks.** Read from GramJS's types and proven against fakes only: `UpdateReadHistoryInbox` (a person's or a basic group's chat: `peer`, `maxId`) and `UpdateReadChannelInbox` (a supergroup's or channel's: `channelId`, `maxId`), the same two inside a difference's `otherUpdates`, and that `messages.ReadHistory` / `channels.ReadHistory` with a `maxId` mark exactly the chat's messages up to there. Telegram's read mark is a high-water mark: every incoming message in the chat at or below `maxId` becomes read, including any the space does not hold (older than the first fill's 30 days, or a message the bridge is still catching up on). The space can only vouch for the messages it holds, so a message that Telegram has but the space does not yet, lower than the newest one the owner saw, is marked read on the phone too (the same as reading past it on the phone). It matters only in the seconds around a catch-up. The bridge tries a mark five times before giving up on a passing trouble (flood wait, dropped connection) and says so to the space (`GAVE_UP` or the code); the chat then stays unread on the phone and read in the space.
- **Sending.** What only the real Telegram shows: that `messages.sendMessage` with the stored random id goes out once and that a repeat inside five minutes is stored once (an early probe saw an immediate repeat stored once; the five minutes are the build's own bound on what is safe, not Telegram's number), what Telegram answers a send into a group or a supergroup with (the shapes `sentOf` reads: `UpdateShortSentMessage` for a person, the `Updates` envelope's `UpdateMessageID` and `UpdateNewMessage` / `UpdateNewChannelMessage` for a group), that the position the answer carries is the one the next live update follows on from (no catch-up after a send: the log must not say `cannot be trusted`), and that a message the bridge sent arrives in its own stream as one of the owner's own with the id the answer gave (the inbox keys both `<chat>:<id>`). A send is as slow as the bridge's three-second poll. A message that is in a busy group's conversation after the page was drawn refuses the press (the same `through` rule as email: read it and press again); watch whether that is too strict for a busy group.
- **Images and videos.** What only the real Telegram shows: that a screenshot sent "as a file" arrives as a `MessageMediaDocument` with `mimeType` `image/png` and no sticker or animated attribute (so the bridge calls it an `image`), that a screen recording sent as a video has `DocumentAttributeVideo` and an MP4 (or QuickTime) body that `downloadMedia` returns whole, and that a document's `size` is its true length. The mapping is proved with objects the library itself builds and reads back (the bridge's `test/gramjs-shape.test.ts`). Whether Safari on an iPhone plays the files Telegram sends is hand test 43.
- **Photos and voice notes.** What only the real Telegram shows: that `client.downloadMedia` on a `MessageMediaPhoto` or a voice note's `MessageMediaDocument` returns the file's bytes as a `Buffer` (it is read from GramJS's types; it picks a photo's largest version itself), that a photo's stated size is its largest `PhotoSize`'s (or the last of a `PhotoSizeProgressive`'s sizes), that a voice note has `DocumentAttributeAudio.voice === true` and Opus-in-Ogg bytes (the inbox serves a voice note only when its bytes begin `OggS`), and that `messages.getHistory` with `offsetId: id + 1, limit: 1` returns message `id` for a person, a group and a channel (how the bridge finds one message again). Whether Safari on an iPhone plays Opus in Ogg is hand test 34. A download is held in memory (at most 10 MB; a video 50 MB), never written to the bridge's disk.
- **Pictures going out.** What only the real Telegram shows: that a repeat of a photo under one random id is stored once (hand test 53 answers it before the product sends to anyone; if it is stored twice, a repeated offer of a picture could double it and the repeat must be taken out for pictures), the codes Telegram answers a photo with (the build's guesses are `CHAT_SEND_PHOTOS_FORBIDDEN` or `CHAT_SEND_MEDIA_FORBIDDEN` for a group that forbids pictures, `PHOTO_INVALID_DIMENSIONS` for a shape it will not take, `MEDIA_CAPTION_TOO_LONG`, `IMAGE_PROCESS_FAILED`; an unlisted code is said as the code and the draft comes back), the caption limit on the owner's account (1,024 assumed, 4,096 with Premium), how much Telegram softens a large screenshot, that `uploadFile` with one worker from a `Buffer` works in the bridge's Bun against the real servers (the library's `getFileBuffer`, read from its source, not run against Telegram), that the upload opens no new session in Devices, and that the answer of `messages.SendMedia` is an `Updates` envelope `sentOf` reads (read from GramJS's types: the position it carries keeps the live line unbroken). Whether Safari on an iPhone hands a photo over as a JPEG through the picker. The page's paste of a screenshot is proved only in Chromium (the e2e); Safari's clipboard is hand test 55.
- **A heavy first fill** is read in one go (`history` max 5000 per chat) and pushed in pages of 200; memory is a few hundred messages at this size.

## Rollback

Stop the bridge (and keep it from being started again by whatever deploys it: if its deployment sets it running on every apply, empty the instance's manifests and secrets, apply, and remove its namespace or unit by hand). It then pushes nothing and holds no Telegram connection. Blanking the two door entries in the secrets file does not work: the deploy refuses a blank entry, and a bridge with a half door refuses to start. What was stored stays (conversations are closed with Close like any; a bookmark restore removes them with everything else since). The Access application and its token may be left in place (a door nothing uses) or deleted in Zero Trust with the token. The migration is not undone by any of this.
