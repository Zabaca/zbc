# Runbook: one calendar event, one conversation

When one calendar event is updated several times, the space's Today and Inbox show only the latest update. Google Calendar mails every update as its own thread (the subject carries the time), so the same meeting would otherwise show up three times as "Needs reply". **One migration (15, store version 16), one-way: bookmark before the deploy, and an undo build keeps migrations 12 to 15.** No new binding or secret.

## What the code does

- **Which event.** `src/calendar-event.ts`. First the iCalendar part (`text/calendar`) when its bytes are in the message: the UID (a Google UID `<id>@google.com` is keyed by `<id>`), plus the RECURRENCE-ID when the mail is about one occurrence of a repeating event (a zoned one is converted to the UTC stamp Google names it by, so both ways give one key); its METHOD says REQUEST (invitation or update), CANCEL (cancellation) or something else (a reply such as "Accepted", which is not event mail). Otherwise the `eid` of Google Calendar's links in the body, only when an RSVP link (`action=RESPOND`) is there. The subject is never the key. Kept on the message as `event_key` and `event_kind`.
- **Only mail the calendar system sent.** A reply or a forward (In-Reply-To or References, a "Re:" or "Fwd:" subject, a forwarded-message line) is a person's and is never keyed; neither is an invitation from another calendar with a typed agenda. A message is Google's by ONE of two marks a person's own mail never has: its `Sender` is `calendar-notification@google.com`, or it has a `List-Id` header (a Google Group's relay, which keeps Google's body under the group's own Sender) AND its text carries Google Calendar's event links. The links alone prove nothing (a forward in any language, with any subject, or a pasted RSVP link carries them), so they never key a message without one of those marks. Both headers are read from Gmail's message as it arrives (Cloudflare mail: from its parsed headers); the store keeps neither.
- **What is closed.** Within one mailbox, the conversation whose event mail is newest (among messages in play: not Spam or Trash, and not one the spam model judged unsolicited) stays. Each older conversation of the same event is closed when it is open, has no message of the owner's (no reply, no draft), holds nothing but event mail, and was not left open on purpose (**a conversation the owner reopens is not closed again**: after a `conversation.replaced` entry it stays open if a person reopened it, a `conversation.reopen` entry by anyone but the calendar, or if nothing new has arrived in it since, which is a reopen in Gmail itself; new mail in it makes it an ordinary update again, replaceable by a newer one). A cancellation replaces the older ones and is itself replaced by a later update. A different occurrence of a repeating event is a different event.
- **How.** A Gmail conversation is closed by the Mailroom at the end of each alarm run (`closeReplaced`, after the sync), Gmail first, the same Close a person makes, up to 20 a run; an account in its backoff or with a lapsed grant is skipped, a conversation Gmail refuses is left alone for an hour, and the alarm is asked for again only when something was closed and more wait. A Cloudflare mailbox's are closed in the inbox alone as the message is filed. The close is stamped `closedBy: calendar` and the audit trail has `conversation.replaced` with `replacedBy` and `eventKey`. Reversible: Reopen. The space does not yet draw the reason ("replaced by a newer update"); the record is there for it. A mailbox on a JMAP server is not covered: a newer update of an event does not close the older ones there.
- **Mail already stored.** Once, from the alarm that the first start after the deploy asks for (`catchUpOnCalendarMail` in `src/durable.ts`, not the daily pass, so it is not a day late; later starts read one setting row and do nothing). Stored mail has neither `Sender` nor `List-Id`, so the Mailroom (`keyStoredCalendarMail`) reads each Gmail candidate again from Gmail (a stored text with one of Google Calendar's event links, or a calendar attachment), 100 a run with the alarm asked for again while more are left, parses it as new mail is parsed, and records its key, or `none` when it is not calendar mail so it is not read twice. The sweep that follows in the same run closes the duplicates. It is done (setting `calendar_event_keys_backfilled`) when every account with a working grant has none left; a lapsed account's stored mail stays unkeyed, and a Cloudflare mailbox's stored mail is not passed over (its new mail is keyed as it is filed). This reads a message from Gmail per candidate, so a mailbox with hundreds of calendar mails takes a few runs.
- **Counts.** Closing is the ordinary Close, so the menu counts equal the rows (the space's `test/nav-counts.test.ts`, which has a meeting updated three times by three senders).

## Before the deploy

1. `bun scripts/inbox.ts bookmark` and note the bookmark (the undo point; migration 15 is one-way).
2. Note the menu counts (`bun scripts/inbox.ts queue`, or the space's left menu: Inbox, Unread, Closed) and how many of the "Needs reply" rows are calendar updates, for the comparison after.

## Apply

An apply of the space (the inbox runs in its Worker): `bunx @zabaca/zbc apply <env> space`. It is the operator's word to deploy.

## After the deploy

1. The alarm the first start asks for reads the stored candidates and closes the Gmail duplicates (a minute or so; `wrangler tail <space worker>` shows `mailroom: reading stored calendar mail failed` only if Gmail refused).
2. Today and the Inbox show one row per meeting that was updated several times; the older updates are under Closed and archived in Gmail. Compare the menu: Inbox goes down by the duplicates and Closed up by the same number; each number still equals the rows its list holds.
3. In Google Calendar, change the time of a test event with an attendee in one of the connected accounts twice. Only the latest update is open; the earlier ones are archived in Gmail. Reopen one of the earlier ones: it stays open after the next push.
4. If duplicates stay: `SELECT gmail_id, event_key, event_kind FROM message WHERE subject LIKE '%invitation%'`. A NULL key with `event_kind` `none` means the real mail shows neither Google's `Sender` nor a `List-Id` with Google's links, or has neither the iCalendar part's bytes nor an RSVP link; capture one real message and replace the fixtures in `test/calendar-event.test.ts`. The fixtures are written to the documented shapes of Google's mail, not captured.

## Undo

Redeploy a build of the old code that still carries migration 15 (the columns stay, unused). Closed conversations are reopened with Reopen, or by restoring the bookmark.
