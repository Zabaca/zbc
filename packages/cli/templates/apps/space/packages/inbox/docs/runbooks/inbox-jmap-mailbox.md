# A mailbox on the install's own mail server: deploy and live checks

What it changes: a fourth mailbox kind in the inbox's store (**migration 18, store version 19, one-way**), the space reading and sending a mailbox on a mail server over JMAP, and the Worker secrets and var that make it work. Why and how: ADR 0001, decision 33. The server side (the API key for the mailbox, the door in front of the server, the exemption from the server's ban on repeated failed sign-ins) belongs to whoever runs the mail server; the JMAP server this was proven against is Stalwart. Everything below runs from the checkout that deploys the install. A worktree has no Cloudflare access, no secrets identity and no mail server; the build proves the code against a fake server (`test-support/fake-jmap.ts`) and nothing else.

The mailbox is `<address>@<jmap-domain>` below, on the JMAP host `<jmap-host>`. Nothing changes for Gmail accounts, Cloudflare mailboxes, Telegram, Claude's door or the send rule, and their suites run unchanged. The counts below are what prove it live.

## The pieces

- **The declaration** lists the mailbox under `hostedMailboxes` (the install's `workspace.json`). The kit writes the Worker's `INBOX_JMAP_MAILBOXES` var from it, so there is no copy to keep equal. The mailbox is served only where the `hostedMailboxes` switch is on.
- **The secrets**, pushed to the Worker by the space instance: one API key per mailbox (named in the declaration, `INBOX_JMAP_<NAME>` in the examples), and, when the server's door is behind a Cloudflare Access application, that application's service token (`JMAP_ACCESS_CLIENT_ID` and `JMAP_ACCESS_CLIENT_SECRET`). The moved Durable Object runs with this Worker's environment, so these must be bound in the Worker's settings and pushed by its instance; the kit's `do-transfer` and `jmap-door` tests pin them.
- **The door.** The only place that speaks to the server is `src/jmap/client.ts`; `src/jmap/allow.ts` is the closed list of what may be asked of it, checked on every request and pinned by `test/jmap-allow-list.test.ts` and the kit's `jmap-door` test. The server's push subscription calls back to the space's push hostname, `https://<push host>/api/jmap/push/<mailbox id>/<token>`; anything else on that hostname is a 404 by design (`test/no-address.test.ts`).

## Before the deploy

1. **The bookmark** (the migration cannot be undone by an older build, which refuses a store at version 19): `bun scripts/inbox.ts bookmark`. Write the value down.
2. **The counts, before.** From a signed-in browser on the space: `await (await fetch('/api/inbox/store/counts', { method: 'POST', headers: { 'content-type': 'application/json' }, body: '{}' })).json()`. The counts come in three groups because the inbox is never quiet: `equal` (must not change), `onlyUp` (may only rise) and `movesBothWays` (reported); `INBOX_COUNTED` in `src/counts.ts` says which table is in which. Write them down, and the eye's list (Inbox, Unread, Drafts, Closed counts; one Gmail conversation, one conversation of each other mailbox).
3. **The server side is in place** (check, do not redo). Never decrypt the mailbox's key to look at it; check only that the entry exists in the secrets file (`grep -c INBOX_JMAP_<NAME> <secrets file>` prints 1, and the same for the Access client id). If the key was rotated, a rotation reaches the space only when the space is applied, so apply straight after.

## Deploy

`bunx @zabaca/zbc apply <env> space` (named; never a no-argument apply). It pushes the secrets above to the Worker, and the build carries the declaration's `INBOX_JMAP_MAILBOXES`. Then, in this order:

1. `wrangler tail <space worker>` shows `inbox: the store object started` and no error. The migration ran: the Gmail accounts, the Cloudflare mailboxes and Telegram keep their rows.
2. **The counts, after.** `equal` unchanged **except `setting`, which rises by one or two on purpose**: the new mailbox keeps its push subscription as a `jmap-push:<mailbox id>` row (and a `jmap-refused:<mailbox id>` row only if the server refused the key), so a rise of 1 or 2 in `setting` is not a false alarm; a rise of more, or any change in `knowledge_entry`, `draft_chat` or the others, is. `onlyUp` only up (the mailbox count rises by one; mail that arrived meanwhile raises the rest), `movesBothWays` reported. The other mailboxes' rows must be as before. The eye's list: the same numbers, plus the new mailbox's entry.
3. The first alarm after the deploy makes the mailbox row and starts its fill (the last 30 days of Inbox and Sent, in pages across alarm runs). Watch it: `bun scripts/inbox.ts jmap` says `filling`, then `live`, with `push: live` (or `waiting` for a few seconds: the server sends its verification within a tenth of a second of the subscription being made, and the inbox completes it in the next alarm). `waiting` for more than a minute is the failure described under "Push stayed `waiting`" below.

**Rolling back** is not undoing the migration. To stop the space using the mailbox without a deploy: delete the API key on the mailbox at the server, or the service token that opens the door; the inbox marks the mailbox refused, says so in amber, retries nothing, and mail still arrives and the mail apps still work. To remove it from the space: take its entry out of the declaration's `hostedMailboxes` and apply the space; the row and its mail stay and it says it is not synced. A build of the old code must keep migrations 12 to 18; only if the store itself must go back, Settings, Restore to the bookmark (which drops everything written since).

## Live checks

There are nine checks, and two need the mailbox's owner. **A refused key is never retried, so a wrong key during these checks costs a deploy, not minutes: if the card goes amber "refused", stop and read the sentence.** Record each result with the time it took. The "mail app" actions below are made with any IMAP client or a script over IMAP against the same mailbox.

1. **The fill equals the server's count.** `bun scripts/inbox.ts jmap`: `messages` is what the space holds for the mailbox. Compare with the server's own count of the same window (the last 30 days of the Inbox and Sent, which is all the fill reads). They agree within a message or two at the edge of the window (IMAP's `SINCE` is whole days; the fill's window is 30 days to the minute), and the space may hold more if a message in the window was since archived (it is kept, read in as Closed once its thread is held) or if mail arrived meanwhile; a difference of more than a few is a failure of the fill. Settings, Mailboxes shows the card live with Sync now.
2. **Arrival (needs the owner).** The owner writes from a Gmail account to an alias that arrives in the mailbox. The conversation appears in the space unread, under the mailbox's pill and in the menu's entry for it, and **notifies** by the mail rule on the owner's phone. Record how long it took from sending to the notification: push should make it seconds; if it is minutes, the push is not arriving (the card's push line says `waiting` or `off`) and the daily pass is what delivered it.
3. **Read in a mail app shows read in the space.** Mark a message seen in the mail app; the conversation shows read in the space within seconds of the push (or on Sync now). Marking it unseen puts it back.
4. **Read in the space shows seen on the server.** Open the conversation in the space; the mail app shows it SEEN.
5. **Close and Reopen both ways.** Archive a message in the mail app: Closed in the space. Close another from the space: it is in Archive on the server and gone from the Inbox. Reopen it in the space: back in the Inbox on the server; unarchive the first one in the mail app: Open again in the space.
6. **A reply goes out from the mailbox (needs the owner).** The owner presses Send on a reply to their own Gmail address. It arrives in Gmail from the mailbox's address, **passing SPF, DKIM and DMARC** (Show original), threaded under their message; it is in the mailbox's Sent when the mailbox is opened in a mail app, and it is held once in the space, filed read and closed, after the next sync (the sync finds the server's copy by its server id and stores nothing new). A new email from the From list does the same. The send rule is unchanged: Claude's `send` is refused without the owner's recorded instruction and the switch on.
7. **The server is down for a minute.** Stop the mail server's service for no longer than a minute (mail for the server waits in the ingest's retry, so never leave it stopped); in the space, Close a conversation: **refused in words, nothing changed in the space or the server**; the card goes amber "not answering, since ..." after a failed sync. Start the service again; mail sent meanwhile is stored by the catch-up, and the card says live. Do not use a wrong key for this: that is the refused state.
8. **A refused key is a state (optional, costs a deploy to undo).** Skipped unless wanted: it needs the key changed on purpose. The fake-server tests cover it (`test/jmap-room.test.ts`, the describe "a refused key").
9. **Nothing else moved.** The counts again, and a Gmail Close made in the space still shows in Gmail, the Cloudflare mailboxes still arrive and send, the Telegram card is live.

## What to know when it breaks

- **Amber "refused"** means the server answered 401, or Cloudflare Access refused the service token at the door (403). Nothing retries. Find which: `curl -s -o /dev/null -w '%{http_code}' https://<jmap-host>/jmap/session` with no credentials is 403 from Access (the door is up); the key and the token are then the two suspects; a rotated key needs the space applied; a revoked token needs a new token minted at the door's Access application and the space applied. **Never retry a refused credential**: the server bans an address after 100 failed sign-ins (and the ingest shares the loopback address), so a refused key is a state ended only by a deploy.
- **Amber "not answering"** is the server or the tunnel in front of it. A small host can be starved of memory and the mail server is the OOM killer's first pick. The inbox retries with the Gmail backoff (30 seconds doubling to an hour).
- **Push stayed `waiting` after the first deploy.** What was measured against a real server: (1) the server POSTs the `PushVerification` to the push address **within 0.1 s of the create**, before the space has read the answer to its create call and written the subscription's token down; the door found no token and answered 404, and the server does not repeat a verification on a 404 straight away. The fix keeps the token (and the verification code, if it comes early, with the id it names) **before** the create call and matches the answer against it (`maintainPush`, `makePush`, `noteJmapVerification`). (2) The server sends verifications **rate-limited and woken unreliably** (its `pushAttemptWait` is 60 s, `maxPushAttempts` 3): a second subscription made within a minute of another's post was not sent until a later subscription change woke the sender. So a verification can be minutes late, and the inbox's own remake after 10 minutes is the net. (3) That remake ran only inside some other alarm and nothing scheduled one, so it was starved; `workAll` now ends by asking for an alarm just after the time an unverified subscription is due to be given up on (`scheduleNext`, `unverifiedDueAt`), and the object's start asks for a run while one is unverified (`hasJmapWork`). (4) A subscription going live owes a sync at once (`completeVerification`), so mail that came before it was live is read in without waiting for another change. If the server logs `Blocked IP address` lines for addresses other than the tunnel's, they are not this: the tunnel connects from the loopback address, which must be on the server's allowed list. Tests: `test/jmap-room.test.ts`, "the push subscription", with `FakeJmapServer.pushesBeforeAnswer` standing for the server's speed. To check after the deploy: `jmap` shows `push: live` within a few seconds of the first alarm, and a mail sent in the minutes before shows up without another change.
- **Mail arrives only at the daily pass** means the push is not working: the card says whether the subscription is `waiting` (the server has not completed it, usually because the push hostname does not answer) or `off` (the server refused it: the sentence names why).
- **A send says "check the mailbox's Sent"** is an outcome nobody knows (the connection dropped after the request left): look in Sent in a mail app, then say in the space whether it went out. It is refused to say "did not go out" when the server's copy is already held. A send never treats an unclear answer as a refusal (`submitOutcome` in `client.ts`).
- **A message shows no files.** Files on mail through the server are named only, and none can be sent from it.
- **The calendar pass is not done for it:** a newer update of a calendar event does not close the older ones here, as it does for Gmail's and Cloudflare's (`inbox-calendar-updates.md`).
- **Claude's script** reads it with `bun scripts/inbox.ts jmap` and in `queue`, `conversation` and `search`; `from` on a new draft names it by address or name.
