# calendar

The calendars of the Google accounts an install has connected, in one place in the space: a Calendar tab (an agenda by day, a week and a month grid, and an event's card), Today's Later today and Tomorrow, and Settings, Calendars. The tab and Today only read, and Settings changes the owner's settings (and makes the owner's booking links); Claude, through the inbox's script and under its send rule, also reads the free time and makes, moves and cancels events ([the space's ADR 0023](../space/docs/adr/0023-claude-reads-the-free-time-and-makes-moves-and-cancels-events-through-the-inbox-under-the-send-rule.md)); and when the owner turns the switch on, the calendar's own alarm keeps a "Busy" block on each of the owner's other calendars for every meeting that makes them busy ([the space's ADR 0024](../space/docs/adr/0024-the-calendar-keeps-a-busy-block-on-the-owners-other-calendars-for-every-meeting-that-makes-them-busy-under-a-switch-the-owner-turns-on.md)). Terms are in [`CONTEXT.md`](CONTEXT.md); why it was built this way is [the space's ADR 0020](../space/docs/adr/0020-the-calendar-is-the-seventh-tab-over-a-store-of-its-own-synced-from-google-by-push-and-it-reads-through-the-inboxs-one-grant.md); how to work in it is [`CLAUDE.md`](CLAUDE.md); the one-time Google step and the hand test are [`docs/runbooks/calendar-google-setup.md`](docs/runbooks/calendar-google-setup.md).

**This package is a library, with no Worker of its own.** The Durable Object class `CalendarDO` (`src/durable.ts`) is exported by the space's Worker (the space package's `src/index.ts`) and declared there as a new class; the tab, Today and Settings call this package's code in the space's Worker.

## What it is

- **A store of its own** (`src/schema.ts`, `src/store.ts`): accounts, their calendars, the events and the push channels, in one SQLite. It is a copy of Google's calendars, read again in full if lost.
- **A sync** (`src/sync.ts`, `src/engine.ts`): for each shown calendar a first full read, then incremental reads from Google's sync token, woken by Google's push notifications, with channels replaced before they end, a slow safety resync, a full read again on a 410, and a backoff on failure. Nothing polls and nothing reads through: the tab and Today read the store.
- **The inbox's one grant** (`src/google.ts`): the calendar asks the inbox's store, in-process, who is connected and for an access token limited to the calendar permission. It holds no refresh token and has no client of its own. Reading uses `calendar.readonly`; the writer asks for a token for `calendar.events` alone for each write and drops it after.
- **A face for the space** (`src/space.ts`; contract the workspace package's `src/calendar.ts`): `calendars`, `agenda`, `event`, `eventsByUid`, `setShown`, `syncNow`, `blocking`, `setBlocking`, `setBlockingAccount`, `bookingLinks`, `makeBookingLink`, `changeBookingLink`, `deleteBookingLink`, each taking the person the space's one sign-in check named and admitting the owner alone. None of them writes an event to Google: the last six change the owner's settings (the busy blocks, the booking links).
- **A face for the inbox, for Claude's script** (`src/inbox.ts`, over `src/writes.ts`): `events` (the free time, from the store, each event with whether it blocks the owner's time), `invite`, `move` and `cancel` (one request each to Google, which sends the invitations; the event is written into or removed from the store at once). It takes no person: the owner's switch and instruction are checked and recorded by the inbox's router before it is asked.
- **The busy blocks** (`src/blocks.ts`, run from the alarm after the sync; the space's ADR 0024): with the owner's switch on, each timed meeting that makes the owner busy on one taking-part account gets a "Busy" block on each other taking-part account's main calendar. The plan is worked out from the store at every run; the writes are paced (20 a run) and backed off on failure; a block's id is derived, so a repeat is a 409 and an unknown outcome is found again. A block is never drawn, never counted busy for Claude and never makes a block.
- **Booking links** (`src/bookings.ts`, `src/booking-slots.ts`, `src/booking-store.ts`, `src/guests.ts`; the space's ADR 0025): the owner makes links in Settings, each with its rules; a visitor with no sign-in opens a link's page on the space's fourth open path, `/book/`, picks a free time, and the calendar holds the time, asks Google (`freeBusy`) whether the owner is still free, makes the event with a Meet link and has Google send the invitation. The visitor's face (`CalendarForGuests`) takes no person: a link's name or a booking's secret (kept only as a hash) is the credential, for moving or cancelling. The event's id is derived from the booking's, so an unknown outcome is found again and never doubled; limits per address, per network address and per link keep it from sending invitations in bulk. The page is the space package's `booking/`; the owner is told by the inbox's notifications, asked in-process by name.
- **Google's notification door** (`src/push-door.ts`): `POST /calendar/push` on the push host, answered by the space's Worker (the space package's `src/worker.ts`).
