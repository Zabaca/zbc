# calendar

The owner's Google calendars, read into the space and kept current: a library with no Worker of its own, run by the space's Worker (the Calendar tab with its agenda, week and month views, Today's events, Settings, Calendars). A booking page is not part of this package. The store keeps three months back and half a year ahead (`CALENDAR_BACK_MS`, `CALENDAR_AHEAD_MS` in the workspace package's `src/calendar.ts`). What it is: `README.md`. Terms: `CONTEXT.md`. Why it is built this way, the token choice and what Google's documents say about push: the space's `docs/adr/0020`. The steps an apply cannot do: `docs/runbooks/calendar-google-setup.md`.

## Working here

- **It is a COPY of Google's calendars, so nothing in it is the only copy of anything.** `CalendarDO` (`src/durable.ts`, the one file that touches the Workers runtime) is a new class declared under `exports` in the Worker's settings (the infra package's `src/space-kit/worker-settings.ts`) (no `state`, nothing transferred, like `LiveDO`), found by `CALENDAR_NAME` in `src/store-access.ts`. A lost or replaced store costs a full read of each calendar and nothing else.
- **The layers are the knowledge app's and the inbox's:** `schema.ts` (migrations as code, appended and never edited, `test/schema.test.ts` pins the count), `store.ts` (every rule about what is kept and how it is read back, over a SQL port, no runtime), `google.ts` (the one place that speaks to Google: the calendar list, events, watch and stop; read-only), `sync.ts` (the order of operations around the awaits), `engine.ts` (what the object does: the methods the space calls and the alarm), `space.ts` (the owner-only face the space calls in-process), `push-door.ts` (Google's notification, answered by the space's Worker on the push host), `event-parse.ts` (Google's event into what is kept, with every piece of untrusted text cut and stripped).
- **The contract is in the workspace package's `src/calendar.ts`, not here.** A method added to the face is added there first (`test/space-contract.test.ts`).
- **Reads get a reading token; the permission to change events is asked for but not used.** Connect calendar asks Google for `calendar.readonly` and `calendar.events` so each account is connected once, before any feature that writes events exists and without a second consent; "calendar connected" still means `calendar.readonly`, and `calendar.events` is only recorded (`CalendarGrant.events`, `account.events`, migration 1) and hinted in Settings. The token the sync is handed is `calendar.readonly` alone: `src/durable.ts` passes `[address, fresh]`, so the inbox's `calendarAccess` level defaults to `read`. Asking for an events token (`level: 'events'`) belongs to a feature that writes events; nothing here may.
- **No refresh token, ever.** The grant is the inbox's: the calendar asks the inbox's store, in-process, who is connected (`calendarGrants`) and for an access token limited to the calendar permission (`calendarAccess`). Nothing here may log, store or return a token; `test/read.test.ts` ("what never reaches a screen") and `test/schema.test.ts` hold that. This package must not import the inbox (its source needs the inbox's declaration alias to compile): the inbox's object name is written again in `store-access.ts` and the space package's `test/wrangler.test.ts` holds the two equal.
- **Event text is untrusted.** Anything new that carries text from Google goes through `cleanText` or `htmlToText` in `event-parse.ts`, and a link is kept only through `httpsLink` or `googleLink`.
- **Secrets and vars:** no secret. `CALENDAR_PUSH_URL` is a var of the space's Worker settings (the install kit's output); `INBOX_GOOGLE_CLIENT_ID` and its secret are the inbox's (the calendar has no client of its own).

## Checks

In a worktree, after `bun install` at the root, from the calendar package: `bun test`, `bun run typecheck`. From the workspace, inbox and space packages: `bun test` and `bun run typecheck` (the inbox also `bun run check`); from the space package `bun run test:e2e` (or `bun test e2e/calendar.test.ts e2e/calendar-lapsed.test.ts`, with `CALENDAR_SHOTS=<dir>` for the screens at 1440 and 390 pixels). A worktree has no Google and no Cloudflare: the sync is proven over a fake Google (`test-support/fake-google.ts`, a `fetch` that answers as Google's documents say), and the real one is the runbook's hand test.

## Where it breaks

- **Its identity is (the SPACE Worker, class `CalendarDO`) and the object's name** (`CALENDAR_NAME`). Changing any is a new, empty calendar, which reads Google in full: nothing is lost.
- **Migrations are appended, never edited or reordered** (`src/schema.ts`). A store a newer build migrated refuses an older one, so undoing a deploy that migrated is a forward fix.
- **Keep `src/durable.ts` free of anything the space's environment would not have.** It reads `INBOX` (the inbox's store), `LIVE` (optional) and `CALENDAR_PUSH_URL` from the space's env; a moved object runs with the env of the Worker that owns the class.
- **Never keep a stub of another object.** A stub whose target was reset or aborted (the inbox's and knowledge's owner-route restarts use `ctx.abort`) is broken for good, and an object holding one fails every call until it restarts itself (this happened once in production). `inboxFor` and `engineFor` in `src/store-access.ts` get a fresh stub per call; `test/store-access.test.ts` holds it.
- **A push is a hint.** `receivePush` is one write and an alarm; never make it call Google. The channel's own secret and resource are its whole defence (Google does not sign a notification); never log a notification's headers.
- **A read that finds a calendar "owed" must always leave it either read, failed with a backoff, or not owed.** An alarm that finds something due and does nothing spins; `nextWake` and `calendarDueAt`/`listDueAt`/`channelDueAt` are the one definition of "owed", and `engine.work` never asks for an alarm sooner than a second on.
- **A sync token keeps the window of the read that made it** (an assumption from Google's pages, unverified until a real calendar has been read), so each calendar is read in full again every 7 days (`FULL_RESYNC_MS`) and a 410 reads in full at once.
- **A lapse is not retried.** The inbox marks the grant lapsed (`calendarAccess` does it when Google refuses); the calendar then asks nothing of Google for that account until the inbox says it is live again.
