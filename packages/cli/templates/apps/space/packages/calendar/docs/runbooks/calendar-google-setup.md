# Runbook: add the calendar to the inbox's Google client, connect each account again, and check it

Any install with the calendar needs these steps once, after the space is built with the calendar and before anyone expects events. Placeholders: `<project-id>` (the Google Cloud project the inbox's Gmail already uses), `<client-name>` (its OAuth web client), `<space-host>` (the space's address, for example `space.northfield.example`), `<push-host>` (the inbox's push host, for example `push.northfield.example`), `<owner>` (the install's owner, for example `tessa@northfield.example`), `<env>` (the install's environment).

- **Who:** the owner, in the Google Cloud console (about 10 minutes), then an apply of the space from a checkout with Cloudflare access and the secrets store's keys (an agent applies only when the owner says), then once per account in the space (about 2 minutes each). An agent cannot do the console part: Google has no API for it.
- **Where:** the Google project the inbox already uses, `<project-id>`, and its OAuth web client `<client-name>`. **There is no new project and no new client**: the calendar reuses the inbox's integration. Nothing below touches any other credential that shares the project, the client's id or its secret, or the redirect address `https://<space-host>/api/inbox/gmail/callback`.
- **What it costs:** nothing. The Google Calendar API is free at this volume; Cloudflare's Durable Object and its alarm are inside the Workers plan the space already runs on.
- **What it changes for mail:** nothing, by construction and by test: the mailboxes' Connect asks for mail's permissions alone and never names a calendar scope, so a calendar permission an admin restricts cannot stand between an account and its mail (the inbox package's `test/calendar-grants.test.ts`). The calendar has a sign-in of its own, Connect calendar in Settings, Calendars, which asks for the calendar's two permissions alone (`calendar.readonly` and `calendar.events`, so that each account is connected once, before any feature that writes events), incrementally; Google adds what the account already granted, so mail's stays. A grant that replaces another is kept on the same mailbox, as it always was; mail catches up from its cursor.

## What this sets up, and why each piece exists

| Piece | Why | Who makes it |
|---|---|---|
| The **Google Calendar API** turned on in the project | Without it Google answers every calendar call with `accessNotConfigured`, whatever the grant holds | The owner, console |
| `calendar.readonly` and `calendar.events` on the consent screen (Data Access) | The permissions the calendar asks for, beside mail's. `calendar.readonly` reads, and is what "calendar connected" needs. `calendar.events` (create and change events; not the full `calendar` scope) is asked now so that each account is connected once; **nothing in the calendar package writes to a calendar or is handed a token that could**: the sync's token is `calendar.readonly` alone | The owner, console |
| Each account's calendar **connected, once** (Settings, Calendars, **Connect calendar**) | A grant carries the permissions it was made with; the existing grants hold mail's alone. This sign-in asks for the two calendar permissions alone and Google adds what the account already granted, so the new grant has mail's as well. The mailboxes' Connect is not changed and never asks for the calendar | The owner, in the space |
| A **Durable Object class** `CalendarDO`, a binding `CALENDAR` and the var `CALENDAR_PUSH_URL` on the space's Worker | The store, and where Google's notifications go | `zbc apply <env> space`, not by hand |
| Nothing for the push address | `https://<push-host>/calendar/push` is the inbox's push host, which already has a DNS record, a certificate and no Access application in front of it. Google needs only https with a valid certificate (its push guide; domain verification in the console "is no longer required") | Exists |

## The console steps

In the project `<project-id>`, signed in as `<owner>`. Google renames console screens often; the names below are the current ones (Google Auth Platform) and the old ones in brackets.

1. **Turn on the Google Calendar API.** APIs and Services, Library: search for **Google Calendar API** and Enable it. (If the page says it is already enabled, nothing to do.)
2. **Add the permission to the consent screen.** Google Auth Platform, **Data Access** (old: OAuth consent screen, Scopes), Add or remove scopes: add `https://www.googleapis.com/auth/calendar.readonly` ("See and download any calendar you can access using your Google Calendar") **and** `https://www.googleapis.com/auth/calendar.events` ("View and edit events on all your calendars") and save. Both are sensitive, not restricted. Do not add the full `.../auth/calendar` scope. Leave the three that are there (`gmail.modify`, `openid`, `.../auth/userinfo.email`): **do not remove one**, or the next consent for mail asks for less than mail needs. A sensitive scope needs no verification review while the project is in testing; the accounts are already test users, and that does not change.
3. **Check the client and the test users are as they were.** Clients: `<client-name>` still lists the one redirect address above (no new one is needed). Audience: with the app External and in testing, every connected account is listed as a test user.
4. **The Workspace admin of the install's own organisation.** Admin console, Security, API controls, App access control: the inbox's app is still **Trusted** (it is, from the mail setup; a Trusted app may be asked for the calendar permission without a new setting). If the consent screen for `<owner>` says the app is blocked, this is the place.
5. **The admins of any other organisation whose account is connected.** An account on another Google Workspace domain has its own admin, who allowed the inbox's app for mail. They are expected to allow the calendar permission on the same app. **To verify** when each account's calendar is connected: if one's consent screen refuses, only Connect calendar is affected (mail is not asked for the calendar and keeps working), the account's card in Settings, Calendars stays "needs the calendar permission", and its calendar can come in by being shared to an account that is connected (free/busy at least, in Google Calendar's own settings) or be left out.

When 1 to 4 are done, tell the agent doing the apply, and say when to apply.

## The apply

```bash
bunx @zabaca/zbc apply <env> space
```

On the owner's word, from a checkout with the secrets store's keys, once the change is merged. It deploys the space's Worker with the new class declared as new (nothing is transferred and nothing is empty-provisioned that held data), the binding and the var. No secret changes. The Calendar tab appears in the space at once; each account's card in Settings, Calendars says the calendar needs its permission until the next step. The apply must not run before the merge: the infra package's tests pin the Worker's file.

## Connect each account's calendar

In the space, **Settings, Calendars**: each connected account shows "Connected for mail: the calendar needs its permission" with a **Connect calendar** button. Press it on each (the account is hinted, so Google offers it first). Google shows its consent screen ("Google hasn't verified this app", as for mail) asking for **only** the two calendar permissions ("See and download any calendar you can access using your Google Calendar" and "View and edit events on all your calendars"); accept both. If one is unticked, the account still connects for reading (reading is what counts) and its card says "Connected for reading. Editing events needs Connect calendar again": press Connect calendar again and tick both. You land on Settings, Calendars with the account live. Within a minute its card shows its calendars and the Calendar tab shows its events.

- **Mail is not touched.** The new grant carries mail's permissions as well (Google adds what the account already granted). **To verify:** mail on the account still syncs and sends after Connect calendar. If Connect calendar answers "Google did not keep this account's mail permission with the calendar's, so nothing was changed", the account's mail grant is as it was: reconnect it in Settings, Mailboxes first, then press Connect calendar again. Nothing was revoked.
- **The weekly reconnect of accounts outside the project's organisation is the mailboxes' own sign-in** and asks for mail alone. **To verify, in the second week:** whether the calendar permission comes back with it (the request keeps what was granted) or Connect calendar has to be pressed again; and that a mail reconnect still works for an account whose organisation restricts the calendar scope. If a mail reconnect is ever blocked, the one parameter to drop from the mailboxes' request is `include_granted_scopes` (the inbox package's `src/gmail/google.ts`, `buildAuthUrl`).

## The hand test

Do these in order, and write down the answers where the question asks for a number or a time.

1. **Each account is live and its calendars are right.** Settings, Calendars: one card per connected account, each "Live", with its calendars. Owned and primary calendars are switched on and holidays, birthdays and other people's are off. Switch one hidden calendar on and its events appear in the Calendar tab within a minute; switch it off and they go.
2. **Each account's next 7 days match Google.** For each account, count the events in the Calendar tab for the next 7 days (use the colour key above the agenda to tell the accounts apart; an event on two of the person's calendars is one row naming both) and compare with the same account's week in Google Calendar. Known differences, not faults: a working-location entry is left out on purpose; an event on a hidden calendar is not counted; a declined invitation is drawn dimmed and struck, not removed. Any other difference is a fault: write down the event.
3. **Push arrives.** In Google Calendar (the web, or a phone) make an event on `<owner>` for tomorrow. **Do not press Check now.** It should appear in the Calendar tab within about a minute. Move it: the row moves. Delete it: the row goes. Do the same on one account outside the project's organisation. **To verify: Google accepts the notification address with no domain registered.** If nothing arrives after 10 minutes, read the Worker's log (`wrangler tail <worker>`) for `calendar:` lines; a `push.webhookUrlUnauthorized` or a 400 on `events.watch` there means Google wants the address registered, and the calendar says so on the calendar's row in Settings ("Live updates are off for this calendar") and falls back to reading every 6 hours. Note what the line says.
4. **What Google granted a channel.** `wrangler tail <worker>` after the first connect shows a line per channel, `calendar: a push channel for <account> (...) lasts until <time>`. **To verify: the lifetime.** Google's pages state a 7 day default and no maximum; write down the time granted. A channel is replaced when it has a day left, which a week later shows as new lines.
5. **The token is narrowed.** The same log shows, once, `google: a token asked for "https://www.googleapis.com/auth/calendar.readonly" came back carrying exactly that`. **To verify:** if instead it says `came back carrying ...` with the Gmail permission in it, Google did not narrow the token: the calendar's token can then read mail. Stop and report it; the code still never uses it for mail, but the design's claim is not true until this reads "exactly that".
6. **A change made while the space is not listening is found.** Make an event in Google, and press **Check now** in the Calendar tab: it is read at once. Then leave an account alone for a day: its events are still right the next morning (the safety resync, every 6 hours, found whatever a notification missed).
7. **Today.** The Later today and Tomorrow lists on Today show Google's events beside Meet's meetings, in time order, each opening its card; an invitation not answered says "Not answered".
8. **An event's card.** Its time has the zone named and is on the company's clock (its declared time zone), whatever the phone's zone; its video call link opens in a tab of its own; "Open in Google Calendar" opens the event in Google.
9. **A lapse is said once.** After 7 days the accounts outside the project's organisation lapse (Google's testing mode): Settings, Calendars and the agenda each say so in one amber sentence naming the account, its last events are drawn marked "Old", and Connect again (the mailboxes' sign-in) ends it; **to verify** whether the calendar permission comes back with it or Connect calendar is needed. **To verify:** whether an account inside the project's own organisation lapses too, as for mail (the console shows the project's organisation). Write down what happens in the second week.
10. **Disconnect.** Settings, Mailboxes, Disconnect on an account you can connect again: its calendar card says "Not connected" and its events are gone; connect it again and they return. Calendar has no Disconnect of its own: one grant serves both.
11. **The permission to change events was granted.** After Connect calendar on each account, no card says "Editing events needs Connect calendar again". **To verify:** a card that still says it after both boxes were ticked means Google did not return `calendar.events` in the grant; report it. (Nothing in the calendar package uses it; a feature that writes events must check it first.)
12. **Mail did not change.** Mail on every account still syncs, sends and archives as before; the Gmail lines at the foot of the menu are as they were.

## If something is wrong

- **Every account says "Could not read ... accessNotConfigured".** Step 1 of the console steps was not done in this project.
- **An account's card says "Editing events needs Connect calendar again".** Its grant has `calendar.readonly` and not `calendar.events`: connected before the second permission was asked for, `calendar.events` missing from the consent screen's list (step 2), or unticked. Reading is unaffected. Press Connect calendar again.
- **An account still says "needs the calendar permission" after Connect calendar.** The consent screen's list did not include the calendar permission (step 2), or the person unticked it, or the organisation's admin restricts it (step 5). Press Connect calendar again and accept it.
- **No push and no `calendar:` line.** `CALENDAR_PUSH_URL` is a var of the space's wrangler file; unset or not https, no channel is made, and the calendar reads every 6 hours. Check the deploy took it.
- **Roll back.** The calendar can be left alone: nothing depends on it. The tab stays and says its accounts need connecting. A Durable Object class cannot be un-declared by an apply that still lists it; undoing is a forward fix in the Worker's settings (the install kit, the infra package's `src/space-kit/worker-settings.ts`).
