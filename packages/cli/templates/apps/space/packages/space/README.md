# space

The front door of a company's workspace (`space.<your-domain>`, `space.northfield.example` for the bundled invented install), and the one Worker that serves it. Glossary and what to know before changing it: [CONTEXT.md](CONTEXT.md).

## What runs where

The space is **one Worker**. The inbox, meet, forms and the knowledge app are parts that run IN it, each over its own store, and the space is the one address people use.

- **One sign-in check per request.** The Worker checks the Access assertion once and hands each part the person it named ([ADR 0015](docs/adr/0015-forms-and-the-knowledge-app-run-in-the-spaces-worker-and-the-knowledge-store-is-handed-to-it.md), [the company layer's ADR 0003](../workspace/docs/adr/0003-the-space-checks-the-sign-in-once-and-the-parts-in-its-worker-are-handed-the-person.md)). Forms' database and bucket are bound by name; the knowledge store is a Durable Object this Worker owns.
- **The inbox** runs here over its own store ([ADR 0017](docs/adr/0017-the-inbox-runs-in-the-spaces-worker-and-its-store-is-handed-to-it.md)): the part (the inbox package's `src/space-part.ts`) is handed the person the check named, Claude's door is checked here and handed to the inbox's router in-process, and the Durable Object class `InboxDO` belongs to this Worker. This Worker is also the inbox's machine entrance (`src/worker.ts`): Gmail's push on the install's push host, Cloudflare's mail, the delivery reports and the daily pass. There is no `INBOX` or `INBOX_AGENT` service binding, and no `SpaceInbox` entrypoint.
- **Meet's chat, channels, calls, Phone conversation, dial pad and live socket** run here over meet's two stores ([ADR 0016](docs/adr/0016-meets-chat-calls-and-phone-run-in-the-spaces-worker-and-its-two-stores-are-handed-to-it.md)): there is no `MEET` binding, and the part (the meet package's `src/space-part.ts`) is handed the person the check named. Where an older note in an ADR says the space binds `FORMS`, `FORMS_READS`, `KNOWLEDGE` or `MEET` to an entrypoint, or forwards the assertion, "Reading an older note" in ADRs 0015 and 0016 says how it reads now.
- **Guests, call links and signers** use three paths of this host that need no sign-in (`/r/` a call, `/w/` a channel's guests, `/s/` a signer: `src/guests.ts`, [ADR 0018](docs/adr/0018-guests-and-signers-use-three-open-paths-of-the-spaces-host-with-no-sign-in-and-a-policy-that-keeps-their-pages-to-those-paths.md)). Their pages are built by `bun run build` after the space's own (`vite.guest-meet.config.ts`, `vite.guest-forms.config.ts`) and are not served by `vite dev`.
- **The page is told, not polling** ([ADR 0019](docs/adr/0019-one-live-object-per-company-holds-every-open-page-and-every-store-tells-it-after-a-change-is-stored.md)): one hibernating `LiveDO` per company (`src/live-do.ts`, bound `LIVE`) holds the one socket of every open tab (`GET /api/live`). Each store tells it AFTER a change is stored (the inbox's, meet's two, forms' database seam, the knowledge store), naming the part and perhaps the conversation and never what changed, and the screens on view read again for that part (`src/client/liveHub.tsx`, `useLive`). The 60 second read is ten minutes now, the safety net for a lost message; the page also reads on reconnecting and on being shown again. Meet's nudge asks the live object who has the space open. Channel guests keep their socket on meet's Workspace object.
- **Nothing else is an address of its own.** No other host serves meet, forms or the knowledge app.
- **The operator's three** for the inbox's store are `POST /api/inbox/store/{bookmark,restart,counts}` (owner only).

```
bun install
bun run test         # the Worker through its real router, the page as markup, the deployed config, the built bundle
bun run typecheck
bun run build        # dist/client (the page) and dist/space (the Worker)
bun run test:e2e     # the Forms tab's screens in a real browser over forms' real Worker (below)
```

Run `bun run build` before `bun test`: `test/sw-build.test.ts` reads the built service worker from `dist/` and skips that check when there is none.

**There is no wrangler file here.** The Worker's settings (hostnames, bindings, senders, mailboxes, crons) are made by the install kit (the `space-kit` folder) from the install's declaration (`workspace.json`) and install file (`workspace-install.json`: the names its stores, Access applications and secrets have). `vite.config.ts` reads the two and the content file (`workspace-content.json`) against each other, writes the settings to `wrangler.json` (gitignored, never edited) and stops the build, with every problem named, if they disagree. `SPACE_DECLARATION` builds another install from its own files, which sit beside it ([ADR 0007 of the company layer](../workspace/docs/adr/0007-the-install-kit-makes-an-installs-instances-and-worker-settings-from-its-declaration-and-install-file.md)). A production build names its declaration, install file and content file explicitly.

`bun run dev` serves it on :4838. Without Access in front there is no assertion, so put `ALLOW_UNAUTHENTICATED=1` in `.dev.vars` in this package (gitignored); the Worker honours it on localhost only. `vite preview` reads the same file from `dist/space/.dev.vars`.

## Seeing screens without the parts

**Stand-ins.** Add `SPACE_FIXTURES=1` to the same `.dev.vars`: with the dev switch on, on localhost only, the Worker asks stand-ins with invented people (`src/stand-ins.ts`) in place of the parts, so every screen is filled without anyone's mail. Use `vite preview` after a build to look at the page: `vite dev` serves React's inline refresh script, which the page's content security policy refuses. A press (a send, a save, a merge, a close, showing a calendar) changes the stand-ins for as long as the server runs.

| `SPACE_FIXTURES=` | What it shows |
|---|---|

Each test file starts its own pair on free ports (`SPACE_E2E_PORT_FORMS`, `SPACE_E2E_PORT_SPACE` name them). The tests need Playwright's Chromium or an installed Chrome, and `poppler` is not needed here (the signed PDF's checks are forms' own e2e). They write `.dev.vars` in this package and in forms for the run and put it back as it was.

Four Access applications answer on this host: the whole host (the space's: `CF_ACCESS_AUD`), `/forms` (`CF_ACCESS_AUD_FORMS`), Claude's door (`CF_ACCESS_AUD_AGENT`) and the Telegram bridge's door (`CF_ACCESS_AUD_TELEGRAM`), and the Clients door has one of its own too. A request is checked against the audience of the application that answers its path (case aside, as Access matches), the header only, never the cookie. Each machine has its own token on its own path, and neither token is accepted on the other's; `src/agent.ts` (and `src/telegram.ts`, its sibling) is the hand-over and the rule in one place, and the path is the declaration's (`apps.inbox.agentPath`, `install.agentDoor()`), not a literal here. What reaches forms is the request as it came with the cookie taken off.

Writes are accepted on `/forms/api/*`, on the POST paths of a conversation (`/api/email`, `/api/email/files`, `/api/chat`, `/api/read`, `/api/close`, `/api/reopen`), on the calls', the channel admin's and chat's own paths under `/api/meet/`, and on the inbox's views (`/api/inbox/<write>`), which also need this host's own `Origin` and a JSON body; everywhere else a write is a 405. Nothing of forms' beyond the two prefixes `/forms/api/*` and `/forms/logo/*` is reachable here: not the signer's pages or API, which are the guest path `/s/` (no sign-in, ADR 0018), and not forms' files (the screens are this bundle's). Why it is built this way: [ADR 0002](docs/adr/0002-forms-is-a-frame-on-its-own-admin-with-a-day-long-sign-in-of-its-own.md) for the two sign-ins, [ADR 0007](docs/adr/0007-forms-screens-are-the-space-s-own-page-and-forms-keeps-the-api.md) for the screens.

**Claude's door is not a place for people to work and not a way to the page**: a signed-in browser on `/agent/inbox` is refused by Access first and by this Worker again. What the Worker refuses there is pinned by `test/agent.test.ts`: no assertion; a person on the door (the space's, Forms' or the agent audience's); one naming a person and the token; an assertion for another audience; an unset or malformed `CF_ACCESS_AUD_AGENT`; the token on any other path (`whoIsAsking` still admits people only); a path under the door that is not `/api/`; a path that climbs out of the door. The door is HTTP, not a method of the inbox's contract.

## Deploy

The Worker is deployed by hand with the install's deploy tool, not from CI: `bunx @zabaca/zbc apply <env> space`. The apply runs the instance's imports first, then the Worker, so the hostname is never served without its gate:

- the whole-host Access application (`space-access`: it names the host and no path, with no bypass; its `aud` output is what the Worker takes as `CF_ACCESS_AUD`, and `apply <env> space-access` alone lets you read it before the Worker deploys), the Forms application on `/forms` (`space-forms-access`), the three guest applications with a bypass for `/r/*`, `/w/*` and `/s/*`, and the applications of Claude's, the Telegram bridge's and the Clients' doors;
- the raw-mail bucket, the delivery-report queue (this Worker is its consumer) and the other stores the instance names.

Why by hand: the space is the single door to everything, so a bad deploy takes the whole space down; a hand deploy lets a person look at the address after it; and every ship of any part restarts all of it. The cost: a change to the code of any part reaches the space only when someone applies it, and a change to the declaration (a person added OR removed) must be applied by hand. Removing is the one that fails open: the space keeps the person in its Access policy and its bundled list until someone applies it.

**Store identity.** The stores' identity is (this Worker, class), and each object's name is a constant of its part. Never rename the Worker, a store class or those object names, and never deploy a file that declares a class live in another Worker. The Worker's settings declare every store class (`KnowledgeDO`, `RoomDO`, `WorkspaceDO`, `InboxDO`, `LiveDO` with no store, `CalendarDO` (a copy of Google's calendars that starts empty and reads Google in full; ADR 0020) and `ClientsDO` (ADR 0021)). The mail routing (Cloudflare Email Routing's catch-alls) names the Worker by its literal name, which is another reason not to rename it. The Clients door's first apply mints its service token: apply that instance alone first and capture the secret.

**Secrets and settings the apply pushes.** Worker secrets come from the install's secrets file: the forms vault's master key, the seal certificate's key and chain, the SFU's two secrets, the phone's secrets (pushed only when all four are present) and the inbox's own. Literals the Worker needs are written down from the declaration, so applying never contacts Google. Forms' bucket and database are instances of their own, applied before the Worker: the database's instance creates it if missing and applies forms' migrations. Forms' hourly sweep is this Worker's third cron, beside the five-minute sweep.

**Another company's install** is its own environment, built from its own declaration, install file and content by the same kit and applied with `bunx @zabaca/zbc apply <env> space`. Nothing of one install's files belongs in another's.

### Putting the space back to the previous version

Rolling the space back is the same apply of the earlier code, made from a separate checkout of it:

1. Make a worktree at the commit (or tag) before the change: `git worktree add <dir> <previous-ref>`. Never switch the branch of a checkout that another session is working in: its next commit would land on the wrong branch.
2. In that worktree run `bun install`, then the same apply: `bunx @zabaca/zbc apply <env> space`. The worktree has no secrets of its own: point it at the install's secrets file the way you do for any apply.
3. Check the address as after any apply (next section), and compare the inbox counts with the ones taken before the change.

What a rollback does not undo: the inbox's store migrates one way, so the earlier code must be one that still reads the newer tables (the runbook of a change that migrates says which build keeps them, "an undo build keeps migrations N to M", and takes a bookmark before the apply to restore from); a migration of Forms leaves its columns in place and the old code never reads them; a store the change created stays and is unused.

### Checking an address after an apply

A first apply makes a new address and a new Access application, so check it from outside, then signed in:

1. `curl -sI https://space.<your-domain>/` with no sign-in: Access's redirect to its sign-in page (a 302 to `<team>.cloudflareaccess.com`), never a page, never a 200. The same for `/today`, `/api/me`, `/assets/`, `/inbox`, `/settings`, `/sw.js`, `/manifest.webmanifest`, `/api/conversations`, `/api/live`: no path answers without the sign-in, and no new path answers a page or JSON. A POST with `-H 'content-type: application/json' -d '{}'` to a write (`/api/email`, `/api/chat`, `/api/close`, `/api/inbox/contact-merge` and the rest) answers the redirect or 401/403, never a 200, a 400 or a 405 from the Worker. The Forms paths answer the Forms application's redirect (its `Location` names the `/forms` application), and `/today`'s names the whole host: two applications answering, which is all a curl can show.
2. Signed in as an owner: the address opens on Today, with Today, Inbox, Meet, Forms, People, Knowledge and Calendar (the install's tabs) down the side (a strip across the top on a phone, with every name readable whole), each tab opening, no horizontal scroll, and the page title naming the company.
3. `/api/me` in that browser: the person, the company and the install's tabs and switches.
4. Zero Trust, Access, Applications: the whole host at 730h with one policy allowing the install's people; `/forms` at 24h with the cookie path setting on; the guest applications with their bypass; the agent and Telegram doors with a service-token policy and no person.
5. Contrast the counts the inbox's operator reads (the inbox package's `bun scripts/inbox.ts mailbox`: messages and conversations, a `live` state) before and after any apply that touches the inbox: they must be unchanged.

### If the two sign-ins disagree

The whole-host application and the Forms one keep apart because the Forms one scopes its cookie to `/forms` (`pathCookieAttribute`), which a live run showed to hold; the reasoning and its limits are in [ADR 0002](docs/adr/0002-forms-is-a-frame-on-its-own-admin-with-a-day-long-sign-in-of-its-own.md). The whole-host application's session cookie is `SameSite=Lax` (ADR 0002, "The space's cookie is SameSite=Lax"); a browser already signed in keeps its old cookie until it ends. The test that the two live together: open `/today` (sign in if asked), then `/forms` (it asks for a code: the Forms application's own), then **reload `/today`** (a click on Today from the Forms tab moves inside the page and proves nothing about the cookie), then open Forms again. Neither may ask for a code a second time. If, after signing in at Forms, Today asks for a code again and Forms then asks again (it keeps happening), check first that the Forms application in Zero Trust shows the cookie path setting on (the apply prints `changed path_cookie_attribute` when it had to set it). Symptoms and what they are:

- **The Forms tab reloads once by itself:** the Forms sign-in had ended under a screen and the page renewed it, as it should. Twice in a row, or a screen saying "Your sign-in has ended. Reload the page to sign in again", is a failure: reload by hand, and report it.
- **A Forms screen that says an error and has no data:** forms answering with an error (a line from forms, not a blank page), or the call losing the Forms session, which reloads the page by itself.
- **Opening `/forms` first, with no space session:** the page goes through Today and comes back by itself (one extra sign-in code, if the month's has ended). A blank page there is the failure. A file of the page that failed to load on `/forms` sends the page through Today by itself (once per two minutes), so a loop or a blank page there is the failure to report.

How long a sign-in lasts is the declaration's (`space` entry, set in `space-access`): the whole host a month (730h), Forms a day.

## Screens and the rules worth knowing

What each part of the page does, and the rules a change must keep. Reasons are in the ADRs; every rule here is pinned by a test.

### Inbox and Meet

The old Conversations tab was split into Inbox and Meet ([ADR 0014](docs/adr/0014-conversations-is-split-back-into-inbox-and-meet-and-the-old-addresses-redirect.md)): `/inbox` is email alone, `/meet` is channels, direct messages, calls and the Phone; every `/conversations` address redirects (302) to the same thing under the new path (a table in `test/inbox-and-meet.test.ts`, and in a real browser in `e2e/inbox-and-meet.test.ts`). Which app each list asks is pinned: the Inbox never asks meet for its list, Meet never asks the inbox. A person who has both mail and chat has **Open email** and **Open chat** on People and Today; a person with one has one. A notification tap opens `/inbox/<address>`; one shown before the split opens the old address and ends in the same place.

- **The Inbox's menu** is the inbox's own, a tree under the tab: Inbox, Unread, Drafts, Bulk, Closed with the inbox's counts; each business mailbox; each Client with its open count; Contacts (opens People); Settings at the foot with Gmail's last push and each mailbox's last mail. On a phone a button above the list says the view and opens the same items in a sheet. A row of the list is a person, so the list can show fewer rows than a count. Drafts lists every person with a draft waiting (closed and Bulk conversations too), and a Client its open conversations Bulk included, so each list matches its count.
- **Rows.** A person linked to a Client has the Client's name as a pill on their row (two pills for two Clients), and one the inbox only suggests a dashed pill with a question mark. A thread with two outside people is one row, under the one who wrote last (a person with a name before a bare address when they tie), saying "Shared thread, with ..." ([ADR 0003](docs/adr/0003-conversations-is-a-merge-of-two-reads-one-row-per-person-joined-by-address.md)). Badges count an unread email conversation as one and an unread chat message as one.
- **Meet's list** shows channels, direct messages, the Phone row and calls with no conversation; New call, New message, New channel, Browse channels; All, Chat, Channels and Calls (and Phone). Both lists are read again when the page is shown again and when the live object says a part moved.
- **Search** gives email results with who is on each; chat results come with "Chat messages cannot be searched yet". A result opens the person's conversation here, beside the list (a whole screen on a phone), in the same tab: the first other person on it (never the signed-in person), found by their address, or by their contact when they have none (a LinkedIn handle). The conversation holds every thread with them, closed and Bulk ones too; it is not scrolled to the thread. A result with no one else on it is drawn and is not a link.

### A conversation

- The history is **one run by time**: each email under a heading with its subject ("with ..." on a shared thread), direct messages under "Direct message", the profile beside it (on a phone, behind a Profile button with a way back). "Earlier messages" appears only if there is more and pages back without a jump (a quote on the first page still folds).
- **Reading an email.** The inbox decides how an email is read: each message of `messagesWith` carries `read` (what the sender wrote now, and the quoted earlier email folded behind "...") and, on an email the owner sent, `to`. The space never decides what is quoted; a message without `read` is drawn whole. Each email is a bubble: the sender's on the left with name, address and time, the owner's on the right in the blue tint with "You to <address>". What the inbox leaves above the fold (a signature or tracking link above the "On ... wrote:" line) stays visible. A message with no quote shows whole, with no button. The space draws no Gmail labels line, no Cc line and no "Claude sent this" badge on a message.
- **An email's calendar part is a card** (`src/client/CalendarCard.tsx`). The inbox reads the part once when the mail arrives and keeps a short summary (its `calendar` on a message, with `fromYou`); the page draws a card from it under the email, in place of the empty bubble when the email has no words (never both), and the file's chip stays under the card. It says what the part is ("Invitation", "Updated invitation", "Cancelled", "Event", or "<guest> accepted", "declined", "said maybe", "proposed a new time: <time>" with the guest's note in their own words), the title, the time on the COMPANY'S clock (all-day events by their days; a time the part gave no usable zone for is said as written and not converted), the place as text, "From <organizer>" ("From you" for the owner's own invitation), the guests (ten, then "and N more"), and "Repeats" or which occurrence. **For the owner, where the Calendar tab exists, the card is joined to it** (`joinCalendar` in `src/conversation.ts`: one read of the calendar's store for the page, `eventsByUid`, that asks Google nothing): "Open in Calendar" opens the event's card, and a reply that carries no title or time takes them from the event. A teammate's answer never asks the calendar and is never given anything of the owner's; the calendar not answering, or an install with no Calendar tab, leaves every card as the inbox gave it. A card has no button that answers, accepts or sends anything, and no link of the stranger's calendar part. The list's line for an email with no words is the summary's one line, made by the inbox.
- **Marking read** marks what is on screen as read in both apps. With a long history, an unread email that is only behind "Earlier messages" stays unread in the inbox after the conversation opens.
- **Replying by email.** The thread to answer is chosen in the box (the newest open one is the default). A shared thread says "Reply all to A and B" and goes to all. Send sends once (a compose key is made when the person starts writing; pressing twice quickly sends one email). Mail goes from the mailbox the thread is in. If a message arrived in the thread since the page read it, Send answers "A new message arrived ... press Send again" in the inbox's words, shows it, and sends the same text on the next press. A direct message goes to the person or posts to the channel.
- **Claude's draft** shows in its own thread at the time it was made, with who wrote it, **To with its address and every Cc with name and address**. A draft made with "copy everyone" (`copyEveryone` in the JSON `scripts/inbox.ts draft` takes) lists every recipient, and so does one with a Cc typed with `cc` (a list of addresses, in the same JSON; the owner's Edit on the card has a Cc box that adds and removes them, and a change is an edit like any other, so it raises the draft's revision); "Send as it stands" sends it once and each receives it. A draft whose Cc the inbox did not say is not sent from the space: the card says so. The draft chat ("Ask the assistant", say "shorter") changes the draft on the card, shows "Revised the draft" and is the inbox's own draft chat; nothing is sent. Claude cannot send: only the owner's Send in the space does.
- **Close and Reopen.** **Close** (the letter `c` with the cursor in no box; typing a word with a c in the reply box closes nothing) closes the open email threads on screen: the button says "Closed.", becomes **Reopen** for as long as the page stays open, the thread leaves Gmail's Inbox and the row leaves the main list (a person with a direct message keeps a row, without the email); the person is under Closed. **Newer mail is not closed**: the page says "A new message arrived in ..., so it was not closed. It is shown now." and the thread stays open; press again and it closes. **Send and close** sends and closes ("Sent and closed."); plain **Send email** leaves it open; it is only offered for a thread that is open and on screen (an open thread older than the page gets plain Send only). A direct message has neither, and a row that is only chat has no Close. **Reopen is one thread**: from the Closed view the header has **Reopen "<subject>"**, naming the newest closed thread (or the closed one chosen in the reply picker), and only that thread comes back (right after a Close made on the page, Reopen undoes exactly what that Close closed). **A thread not on screen is left open**: an open thread behind "Earlier messages" is not closed, and the page says how many were left open.

### People

([ADR 0009](docs/adr/0009-people-is-three-reads-merged-by-address-and-the-profile-is-the-inboxs-contact-with-three-fields.md).) The inbox's store gained, in a one-way migration, four columns on `contact`: the business, the role, a note and the revision a write names.

- **The directory** at `/people`: **Clients** (people the inbox has linked to one of the space's Clients), **Outside** (every other contact the inbox judges a person, and channel guests) and **Team** (the company layer's people, and meet's teammates), by name, with a box to find someone. No channels. The number at the top is people, not contacts. Newsletters, receipts and no-reply addresses (the inbox's own judgment) are counted in a line at the foot and not listed, with **Show automated (N)** under it to list them under an Automated heading, so a real person the inbox misjudged is found; their page opens either way with its fields. A row says the person's business and role, or their address, and shows their Client.
- **A person's page**, `/people/<key>`: for someone outside the team, their inbox contact (name, every address and number) with **Business, Role and Notes** to fill in and Save, the **Client** they are linked to (or the one the inbox only suggests, with a **Link** button, or a list of the space's Clients to choose from, and **Take out**), **Merge with another entry** for two entries that are one person, **Rename** (a box starting from the name as it is now; the inbox's refusal of an empty name is shown under it), **Split off** beside each address of a person who has two or more (none for a person with one: the inbox keeps a contact's only address; splitting opens the new contact, named by the address), and the **documents** forms lists for their addresses (title, state and how many have signed; each opens in Forms; nothing else of a document, never another recipient's name). For a teammate, the company layer's person (role, address, the address their sign-in goes to), no boxes, no Client, no merge. **Open conversation** opens their conversation; for someone nothing has been said with there is none (for instance a contact the inbox made for a draft), and the page says so. The same three fields sit beside a conversation, saved from there.
- **A save names the revision the person was shown.** If they changed since (another window, Claude's script), the inbox refuses, nothing is saved, and what was typed stays in the boxes with the newer details under it and a button to take those instead. Rename and Split off name the revision the same way and say so when the person changed.
- **A merge asks first, and can be undone.** It says what moves (their addresses and conversations go to the person kept, who keeps their own name and Client; a business, role or note left blank is filled from the other), and the line that follows has **Undo**, which puts the other person back with their name, Client, details and addresses. A merge is refused when either person changed since they were shown.

### Documents in a conversation

A document can be sent for signature from a conversation, and the conversation shows it as a card ([ADR 0010](docs/adr/0010-a-document-sent-from-a-conversation-carries-one-ref-and-is-found-by-any-and-the-card-is-forms-read-drawn-by-time.md)).

- **Send for signature** is in the conversation's header (an icon alone on a phone). It opens Forms' Send screen with the conversation's person already the first signer (their name, and the address they write from now, with the others the space knows for them to choose from; boxes already typed in are not overwritten), and a line over the screen saying it came from that conversation, with a way back. A **channel** names no one to sign (meet does not say who is in one), so the signers are for the person to name, and the document still belongs to the channel. Forms' own Send does the rest: the draft is made, the email is shown, and nothing leaves until the person presses Send there. **Nothing is emailed into the conversation**: forms emails the signed copy to everyone, and the only mail this causes is forms' own signing email.
- **A card** for each document sent from the conversation: its title, its state ("Draft, not sent", "Out for signature, 1 of 2 signed", "Signed and back", "Declined", "Expired"), when it last moved, and a button that opens it in Forms. It sits among the messages at the time it last moved, so a document that completes comes back further down: the **same card** then says "The signed copy is back. Forms sends it to everyone who signed." and its button reads "Open the signed copy". A document sent from Forms to the same person (no conversation) is on the person's page in People and is **not** a card here.
- **Never on a card:** the name of anyone who has not signed, an address, a link, an answer (private or not) or a file's name. A document holding a private answer is drawn exactly as any other, with its title and state; forms' read has no field for what it holds (the workspace package's `src/forms-for-space.ts`).
- **Forms not answering leaves the conversation as it was**, with one line over the history ("Forms could not be reached just now, so the documents sent from here are not shown.").
- **The ref.** An envelope has `conversation_app` (`inbox` or `meet`) and `conversation_id` (forms' migration `0004_conversation.sql`: two nullable columns and an index, both null for every envelope sent from Forms). It is a **conversation ref**, `{ app, id }`. A person's conversation is a merge, so a document carries **one ref** (the inbox's contact for the mail side, else meet's conversation) and is found by **any ref the conversation has** (`refsOf` in `src/conversation.ts`, forms' `documentsIn`). Refs are stored ids, not the row's key, which changes when a person gains an address. The ref lives in the envelope's columns and in **no event** (every event is sealed into the PDF each signer receives). **Known gap:** a document sent from a contact later merged into another stops showing as a card (People still lists it); the fix direction is in ADR 0010.
- Today's **Signed and back** opens the conversation a document was sent from (a document sent from Forms, or whose conversation is closed, still opens in Forms).

### Files and bounces

For a business mailbox's mail only. A Gmail account keeps its rules: its pictures are fetched from Gmail and shown as thumbnails, its other files are named and open in Gmail, and it sends no files. The inbox's `messagesWith` carries each message's `attachments` and, on a reply sent from a business mailbox, what Cloudflare reported of it (`delivery`), and each thread says whether a reply may carry files (`canAttach`); the inbox stores them in its own table, queue and event subscriptions (see the inbox package's runbook `inbox-cloudflare-mailbox.md`).

- **A file on a message** is a thumbnail (a picture) or a chip (anything else) under it. A chip saves the file. Both are asked of this Worker, `/api/attachment`, behind the sign-in; there is no address that works signed out.
- **Attach files** is in the reply box when the thread is a business mailbox's (and is not offered for a Gmail thread, or for a new email until a business mailbox is chosen as From). The files chosen are listed with an x to take each out, and the box says at once if they are too many, too large or empty; Send waits until they are fine. Files chosen and then moved to a direct message or to another thread are never dropped quietly: nothing is sent and the box says why.
- **A reply that bounced** says so under it in red with the receiving server's reason; one that arrived says "Delivered to ..." quietly (about a minute after the send); one that was delayed says it is still trying.

### Writing: a new email, an edited draft, a thread called spam

- **New email** is a button beside New call over the list. The box has **To** (any address; the people the space knows are offered as you type, and "Name <address>" is read as the address), **From**, **Subject**, the words, and **Attach files**. **From** is **Automatic** (the inbox's own rule: the mailbox the person last wrote to, so a customer hears from the business mailbox and a client from the owner, else the Gmail account), **Your Gmail**, or each business mailbox by name and address. The sender is always a mailbox's own address, never anything typed. **Files go from a business mailbox only**, so Attach appears when one is chosen, and files already chosen are never dropped quietly when the person changes to Gmail: Send waits and says why. **Send email** sends once (a key made when the person started writing). If the inbox refuses, in its words (an em dash, an address that is the install's own, no subject), the words stay and pressing Send again after the fix sends. If the inbox cannot say whether it went out, or the space loses track of it, the box says so, offers no second try with the same words, and links to the conversation. When it went, **the person's conversation opens with the email in it** (a message the owner sends is filed read and closed, as the inbox files one, so it is in the person's history and under Closed, not in the main list).
- **The inbox says what it can do** (`capabilities` on its `mailboxes` answer, which the New email box reads anyway). The space refuses, in words and before anything is sent, a new email that picks a mailbox or carries files unless the inbox lists `new-email-from-and-files` ("The inbox has not been updated to send a new email from a mailbox you choose or with files ... Nothing was sent."), because an older inbox would not refuse it: it would ignore `from` and `attachments` and send from the mailbox the person last wrote to, leaving the files out without a word. The From box then offers Automatic only, with a line saying why. A plain new email (Automatic, no files) and every reply need nothing new. Nothing is retried by either.
- **Edit** on a draft's card opens the subject and the words, and, on a reply, **Copy everyone on the message it answers** (as the inbox's card does). **Save** writes them at the revision the card shows; if Claude or the assistant changed the draft meanwhile, nothing of the person's is saved, the card shows the draft's new subject, who it copies, why it was drafted and its words beside theirs, says who changed it, and they choose **Keep mine** (their words stay, now over the revision they have seen) or **Use the new words**. "Send as it stands" waits while the person is editing, so what goes out is never unsaved. An em dash can be saved, with a word that the send will refuse it. The assistant's chat stays on the card while the person edits (a revision it makes shows as the draft having changed). A draft whose send Gmail never confirmed is not editable.
- **Mark as spam** sits at the right of each email thread's heading, and **Move to the Inbox** on a thread that is in Bulk: the inbox's own two buttons. The thread goes to Bulk (kept apart from people, never deleted, nothing changed in Gmail) and stays there (nothing is asked of the spam check again, and a later message does not undo it). A notice says where it went, and says so when the inbox's rules kept it where it was. The button is drawn where the inbox says (`canMarkSpam` on the thread: in a mailbox, and in Bulk or with nobody on it linked to a Client, **any contact on the thread, not only the person**).
- **A send Gmail never confirmed** has this card: "Sending, or the send never finished. Gmail did not say whether this went out, so it has not been sent again. Check Gmail Sent, then say which it was." (from a business mailbox: Cloudflare did not say, "There is no Sent folder for it: ask <the recipient>"), no Send and no Edit, and two buttons: **It went out: remove this** (**record it as sent** for a business mailbox) and **It did not go out: make it a draft again**. Each asks once more on the card and says what it will do ("If it did go out, sending it again delivers it twice"); only the question's **Yes** settles it. A refusal comes back in the inbox's words (Gmail's own copy is already held, so it did go out; it was settled already) and the card is read again. The first time such a send is stuck, it is the one live proof (`scripts/inbox.ts drafts` shows it as `status` `sending`).
- **A text or a LinkedIn draft** (a channel the inbox cannot send on) has **Copy address**, **Copy words** and **Mark sent**, and no Send: "The inbox cannot send a text message. Send it yourself, then press Mark sent." Marking it files it, read and closed, in that person's conversation for the channel, and the message has **Not sent after all**, which makes it a draft again. An email draft has Send and no Mark sent. The note under a text's or a note's composer says Claude can draft a text, which waits on the page to send by hand and mark sent; a draft the space will not send says why and links nowhere; an email cut at the inbox's cap says the rest is in Gmail if it came that way (the space has no screen to read an email past the cap).
- **Drafts on no conversation** (a first email Claude drafts to a new address, a first LinkedIn message to a new contact) are listed in **Inbox, Drafts** under **Not on a conversation yet**, above the people with a draft on a conversation, and each opens at its own address, `/inbox/draft/<draft id>`. The page is the card a draft has in a conversation, with the same actions: **Edit** (at the revision shown; a draft changed since is shown beside what was typed), **Send as it stands** (an email: a compose key made once, the revision shown and no position, because a draft on no conversation has none), **Copy address**, **Copy words** and **Mark sent**. The card shows who it is to and every address it copies before it can be sent. **The address keeps working**: asked of the inbox (`draftAt`, a read of one message by id), a draft that has since been sent or marked sent, or that is on a conversation, opens the person's conversation (`mail:<contact id>`) and the page replaces its own address so Back does not return to a redirect; a draft that was deleted, or an id that is none, says so in words and goes back to Drafts. Today's "Drafts not sent" opens a new email's draft at this address too. Rules, all the conversation's own: the owner alone, a compose key that sends once, the revision shown for a send and an edit, a stuck send settled by saying how it went and never sent again. **Not here:** the draft chat (a draft on no conversation has no conversation to chat about) and a draft whose Cc the inbox did not say. A contact's key lookup asks the inbox for the contact by id, so a person older than the newest 200 conversations is found; a contact's key reads meet too.
- **Load older**: an Inbox list (Inbox, Unread, Sent, Drafts, Bulk, Closed, a mailbox, a Client) is the newest 200 conversations of its view. When there are more, its foot says so and has **Load older**, which shows the next 200 below the rows already shown; the list stays that long through every refresh and a different list starts again from its newest. A mailbox, a Client and Unread are narrowed by the inbox before the list is cut, so each holds what its menu count counts. The menu's counts are never cut. ### Today

- **Happening now:** calls with someone in them that the owner made. **Later today** and **Tomorrow:** meetings with a time. **Waiting on you:** open mail outside Bulk whose newest message came in, unread mail, unread direct messages (each says "Needs reply" and/or "Unread"; a thread two people are on is one row naming both; one the owner already answered, a newsletter and a closed one are not; a long list shows the newest twelve and "N more"). **Drafts not sent:** the inbox's drafts and forms' draft documents. **Waiting on others:** documents out for signature, with who has not signed. **Signed and back:** documents completed since midnight **in the company's time zone**.

### Channels

([ADR 0012](docs/adr/0012-channel-admin-is-meets-answer-drawn-in-the-conversation-and-the-invitation-is-the-one-email-it-causes.md); meet's side is its ADR 0007.) Every rule is meet's, asked as the same teammate, and shown in meet's words; the space draws a button only where meet's `may` says the person may.

- **Where it is.** The Meet list has **New channel** and **Browse channels** under the search box. A channel's conversation has its people where a person's profile is (beside the history on a computer, behind **Profile** on a phone): the people with a tag (the company's, Guest, Invited) and what the person may do with each (Take out, Remove from workspace, Delete everything, Message), **Add someone you can see**, **Invite a guest** (name, email address, **Invite**), and **Rename**, **Leave** and **Archive**. A channel with nothing said in it has a row from the moment it is made ("No messages yet."). A private channel the person is not in is not listed and cannot be opened by its address (it says there is no such conversation).
- **Routes.** `GET /api/meet/channel?conversation=<n>` and `GET /api/meet/browse` (the open channels not joined: a name and a count); `POST /api/meet/channel-create` (`{key, name, privacy}`), `/channel-invite` (`{key, conversationId, name, address}`) and `/channel-change` (`{do, conversationId, name?, personId?}`, `do` one of `join`, `leave`, `rename`, `archive`, `add`, `take-out`, `remove-guest`, `delete-person`). Each is one call to meet with the request's assertion, a `ViewAnswer` with a 200 (a refusal in meet's words, a fault and an unknown outcome are answers the page shows), a body that is none of them a 400, and a write **never retried**; the writes are POSTs on their own paths, accepted by the one POST guard (this host's Origin, a JSON body), and anything else on them is a 405. Making a channel and inviting a guest carry a compose key made for the press, which meet holds (pressing **Make channel** twice quickly makes one).
- **The invitation is the one email, and meet sends it.** The space sends nothing. When **Invite** is pressed meet adds the guest and sends the invitation from the install's meet sender, linking to the guest's own door (which the space itself never links to), once per compose key. Typing in the boxes, making a channel, joining, adding, taking a guest out and archiving send nothing. A guest never reaches the space.
- **Archive** asks first ("Archive this channel? It leaves everyone's list and takes no new messages."); **Keep it** archives nothing. Only its maker and the owner are offered it.

### Connect Gmail and Connect again

Both start and end on this host (`src/gmail.ts`). The redirect address `https://space.<your-domain>/api/inbox/gmail/callback` must be registered on the install's Google OAuth client by hand (Google has no API for it; the steps are in the inbox package's `docs/runbooks/inbox-google-setup.md`). Settings, Mailboxes and spam check, Gmail connection: **Connect Gmail** or **Connect again** is a link to `/api/inbox/gmail/start`. It goes to Google's consent page, and Google sends the person back to the same Settings page with the connection shown (**Connect again replaces the grant with a new one for the same account**). `redirect_uri_mismatch` on Google's page means the console entry is not saved or has not counted yet: wait and press again, nothing was changed. A refused sign-in (another Google account, a refused permission, a code Google would not take, a sign-in that took over ten minutes) is a short page in the inbox's own words with a link back to Settings; nothing is kept.

How it is kept safe (`test/gmail-connect.test.ts`): only the owner's sign-in starts it (the inbox decides; a teammate gets a 403 page with no cookie and is sent nowhere); a return is accepted only with the check Google carried back equal to the cookie, and the cookie is spent on every try, so a forged return (no cookie, another check, none, a cancelled sign-in, no code) asks the inbox nothing and a replay finds the cookie gone (and Google accepts a code once); the browser is only ever sent to `https://accounts.google.com`, whatever the inbox says; only a GET does either (a HEAD and every write method are 405); the client secret and the grant never reach this Worker, only the code does; no sign-in is a 401 on both paths and on every method.

### Knowing a part is down

The tests prove each part down in turn, a slow one and a refusal; the stand-ins (`mail-down`, `chat-refused`, `forms-down`, `calendar-down`, `knowledge-down`) show the notices. A part that does not answer draws its notice and everything else works.
