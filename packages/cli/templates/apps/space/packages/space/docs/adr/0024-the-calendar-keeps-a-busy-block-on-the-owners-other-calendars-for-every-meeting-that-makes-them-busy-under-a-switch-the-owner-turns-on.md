# The calendar keeps a "Busy" block on the owner's other calendars for every meeting that makes them busy, under a switch the owner turns on

Status: accepted. **Amends [0020](0020-the-calendar-is-the-seventh-tab-over-a-store-of-its-own-synced-from-google-by-push-and-it-reads-through-the-inboxs-one-grant.md)** on one sentence (the sync never writes: the calendar's alarm now also makes and removes blocks, after the sync, with a token of its own for the run) and **[0023](0023-claude-reads-the-free-time-and-makes-moves-and-cancels-events-through-the-inbox-under-the-send-rule.md)** on one sentence (only a write Claude makes on the owner's instruction asks for the write-level token: a run of the blocks asks for it too, for the account it writes to). The company layer's [ADR 0002](../../../workspace/docs/adr/0002-one-service-token-comes-through-the-space-on-one-path-to-one-app.md) is not amended: Claude still has one path, to the inbox, and no new method of the inbox's face exists.

## Why

An owner with several Google accounts is busy on one calendar and looks free on the others, so a person who books against another of their accounts picks a time that is already taken. The space already holds every connected account's events and already knows which make the owner busy (not declined, not marked as free time), and it already holds a grant that was asked, once, for the permission to change events. What was missing was a way to keep the others looking as busy as the one, without the owner copying blocks by hand.

## What is decided

### 1. One switch and a tick for each account, in Settings, Calendars

The switch ships off and only the owner flips it. Each connected account has a tick for whether it takes part (every account does at first): a taking-part account gives its busy times and receives blocks, and one that is not ticked does neither. Both are settings in the calendar's own store (`blocking`, `account.blocks`), changed through the space's face (`setBlocking`, `setBlockingAccount`, owner only like every method there) and shown by `blocking`. None of the three writes to Google: each stores the setting and owes the calendar's alarm a run.

### 2. What gets a block

A timed event (not all-day) on a shown calendar of a taking-part account that makes the owner busy (not declined, not marked as free time; tentative and unanswered make them busy), that has not ended and starts within the next 60 days. Each other taking-part account that does not already hold the same meeting (the same iCalendar id and start, held busy: a copy the owner declined there does not hold it) gets one block on its main calendar. A repeating meeting is blocked per occurrence, inside the window, which rolls forward as days pass; a meeting further out is blocked when it comes inside.

### 3. What a block is

An event that says "Busy" and nothing else: no title, guests, place, description or link from the meeting; private; opaque; no reminders; made and removed with `sendUpdates=none`, so nobody is told. It carries three private extended properties (which belong to the copy on that calendar and which no guest's invitation can carry): the key of the meeting it stands for, the account it is on and the key of the install that made it. `parseEvent` reads the mark back, so the store knows the event for a block, and a block is **never drawn** in the agenda or Today, **never counted busy** in the free time Claude reads, never found by an email's calendar card, never a thing Claude's move or cancel can name, and **never the source of another block**: every read of the events table for a screen or for Claude leaves out `block IS NOT NULL`.

### 4. One meeting, one id: a repeat is refused, and an unknown outcome is found again

A block's Google event id is derived from the install, the meeting (its iCalendar id and start) and the account it is on, hashed into the letters Google allows for an id (a to v and 0 to 9, here 32 of them). Making the same block twice is therefore refused by Google (409), and that is read as "it is already there": the same body is sent as a change that also says confirmed, which leaves a live block as it was and makes a block that was once removed live again (Google keeps a deleted event's id, so an insert of it is a 409 for ever). A block whose making had an unknown outcome (Google made it, the answer never came) is found again by its id and never doubled.

**A block is known without its mark.** Three ways, in order: the mark Google gives back; the mark the store already held for that row (a read that brings none keeps it, a full read included); and the id, since an unmarked event on an account's main calendar whose id this install would derive for some meeting the store holds, for the account it is on, **and** that is shaped like a block (titled "Busy", organised by that account itself, no other guest) is marked as the block it is. The id is not a secret (it is a hash of things a guest of the meeting can know), so the shape is the check: an invitation made with a guessed id is an ordinary event, drawn and busy, never made over and never removed by the writer. A block that stops being shaped so (the owner renamed it) is an ordinary event again as soon as it is read: drawn, busy for Claude's free time, never changed or removed by the writer, and a source of blocks like any other meeting (the safer side: the owner made it a real commitment, and one more "Busy" costs less than a double booking). So a Google that did not return the private properties does not turn a block into a meeting that is blocked in turn, and switching off removes such blocks all the same. (A block whose meeting is gone and whose mark the store never held, as after a lost store, is the one case that is not known; the hand test is where this is checked.)

**Two spaces on one Google account.** The install key is hashed from the install's own declared company id, so it is the same after a lost store and says nothing of the company, and it is in the derived id and in the mark. Each install makes, changes and removes only its own blocks. A block of another install is treated like this install's own for every read: hidden from the agenda and Today, never counted busy, never a meeting to block, and never touched. Where another install already holds a block for the same meeting on a target, none is made there (the meeting is blocked once); if the other's goes, the next run makes this install's own. Two installs that both act before either has read the other's block will make one each, and that is accepted. A block left by an install that is gone for good is never removed by the other, which only waits on it.

### 5. The blocks follow the meeting

The plan is worked out again from the store at every run, never kept as a list of things to do: what should exist is a function of the meetings, the settings and which accounts can hold a block; what does exist is the blocks the store holds, read back from Google. The difference is the work, in this order: make what is missing, change an end that moved (a patch), remove what stands for nothing. A meeting that moves is a new meeting key, so its block is made at the new time and the old one removed. A block is removed when its meeting is cancelled, declined, marked as free time, out of a shown calendar, or held by the target after all; when the switch goes off (every block, past ones too); and when its account stops taking part. **An account that cannot be written to at that moment (its sign-in ended, it lacks the permission to change events) keeps the blocks it holds when the switch goes off or it is ticked out**: they go when it can be written to, and its line in Settings says how many stay. A block on a main calendar the owner has hidden is not even held in the store, so it is not removed while that calendar stays hidden. A block of a meeting that has ended is left as it is while the switch is on. Nothing is removed for want of a meeting until every taking-part account has had its calendars read once, so a store made new, or a calendar that cannot be read just now, does not take down blocks that stand for meetings not yet read in. While a calendar's first read keeps failing, that hold is said in the one sentence in Settings, so it is never silent.

### 6. It runs from the calendar's own alarm, with a write token for the run

After the sync, in the same alarm, the calendar works out the plan and does as much of it as the pace allows: at most 20 writes a run, the rest owed another run five seconds on. A failure is a sentence and a backoff that doubles from 30 seconds to an hour; a decision about one write (a 400, a 404) is kept as the sentence and the other writes go on, with that write tried last from then on (so one that cannot be done does not fill every batch), and with no backoff when the rest of the run was done; anything that is not a decision (no answer, a 5xx, a rate limit) or an account that cannot be written to stops the run and backs off. The owner's own change clears the backoff and is tried at once. The token is asked of the inbox in-process, as Claude's writes already do (`calendarAccess(address, fresh, 'events')`, through the calendar's writing client), so the calendar still does not import the inbox; the run's writing client (`createRunWriter`) asks for one token for each account when its first write needs it and drops it when the run ends. Nothing keeps one between runs. An account whose grant lacks the permission to change events, whose sign-in ended or whose main calendar is hidden is not written to: Settings says so beside its tick, with the button that cures it (Connect calendar, or Connect again).

### 7. Settings says how it stands

The switch, each account's tick, how many blocks are kept (this install's, on main calendars, that have not ended), and one amber sentence when blocks could not be written or removal is held back for a calendar that cannot be read.

## The rule

This is the first write the space makes to Google that the owner did not ask for event by event. The rule is: **a standing setting the owner turned on is the owner's word for exactly this kind of write**, a bare "Busy" block on their own calendars with nobody notified, and for nothing else. It is not the send rule's instruction (there is none to record for a thing the owner's setting does), and it opens nothing wider: invites, moves and cancellations of real meetings stay Claude's, on the owner's instruction, through the inbox's router; the calendar's own writes are limited by what `src/blocks.ts` can ask (an insert, a change of end and a delete of an event carrying its own mark, always quiet), the space's face still has no method that writes an event, and the contract test holds both lists. Turning the switch off takes the blocks down.

## What is not here

Any other feature of a calendar-assistant product (habits, task scheduling, smart meetings; scheduling links are [0025](0025-a-booking-link-is-a-public-page-where-a-visitor-takes-a-free-time-and-the-calendar-makes-the-event-with-the-link-the-owner-made-as-the-word-for-it.md), a separate feature of the calendar); the meeting's real title on a block; a rule for one direction only (this account blocks that one but not back); non-Google calendars; blocks on a calendar that is not an account's main one.

## What only the hand test settles

That Google keeps and returns a private extended property set on an inserted event (the whole feature leans on reading the mark back; a Google that dropped it would make each block again at each read, so this is the first thing to look at); that a patch with `status: confirmed` on an event that was deleted makes it live again (the unverified assumption behind reading a 409 as "already there"; if Google refuses it, every block that is wanted again after the switch goes off and on, or after a meeting moves back, is refused, said in the sentence, and the rest of the work goes on); that `sendUpdates=none` really tells nobody; that a block in a calendar Google shows as private reads as "Busy" to a person who books against it; and that an id of 32 letters a to v and 0 to 9 is accepted. The fake Google answers as the documents say, written by the same person who wrote the code.
